## 一、Memory 是什么，业界怎么做

### 1. 为什么 Agent 需要 Memory

**大模型本身不记事，但 Agent 要干活必须记事，这个矛盾逼出了 Memory。**

大语言模型每次调用都是无状态的——它不记得上一次说过什么，全靠调用方把历史塞进 context window。但 Agent 要多轮对话、要跨会话记住用户、要执行长任务，就必须记得住东西。而 context window 有限且昂贵：token 越多越慢越贵，还有硬上限。所以 Agent Memory 的本质是：**在有限的 context window 之外，管理一套让 Agent 记得住东西的机制。**

这件事在 2026 年被推到台前，原因很直接：它是 Agent 从 Demo 到生产要跨的头号坎之一。一个 Agent 周一能通过全部评测，周三却忘了用户的名字——这不是模型问题，是记忆问题。Demo 能跑，是因为整段对话塞得进一个 context window；生产会崩，是因为真实用户会跨会话、跨天、跨话题地回来。

落到 YokeOS 的需求侧：「用一段时间后，Agent 自然记住用户的偏好、项目信息、关键决策，下一次对话不需要重新解释」——这是 Agent 底座区别于 chatbot 的核心体验（[需 §5.6]）。

### 2. 短期记忆与长期记忆

**短期记忆是这一次对话的「工作台」，长期记忆是跨会话的「仓库」。**

**短期记忆**（工作记忆）就是当前对话或任务的上下文：本轮对话历史、刚调用 Tool 的结果、任务的中间状态。容量有限、生命周期短、访问快；对话结束或窗口满了就没了。在 YokeOS 里它就是 Session（SQLite 持久化，按 Channel + 用户 + Agent 联合标识）。

**长期记忆**是跨会话、跨时间持久保存的东西。用户上周说过喜欢某种语言、项目叫什么，这次对话还记得——这就是长期记忆。它不在 context window 里，而是存在外部，需要时检索出来拼回上下文。认知科学里它还细分三类：**情景记忆**（具体发生过的事）、**语义记忆**（抽象事实与知识，如用户偏好）、**程序记忆**（怎么做事的流程，常沉淀为技能或规则）。YokeOS 第一阶段的两层 = 会话 + 长期，情景记忆明确放扩展阶段（[需 §5.6]）。

两层之间有一个核心循环：短期记忆里重要的东西被固化成长期记忆写出去；长期记忆里相关的东西，用时被检索回短期记忆拼进上下文。

### 3. 两个容易混的概念：上下文压缩 vs 记忆压缩

**上下文压缩管「当下这轮说的话」，记忆压缩管「存下来的仓库」，作用的层面完全不同。**

**上下文压缩**解决当前对话太长、窗口快满的问题——把已有上下文变短（总结、裁剪），作用在**当前这次交互**层面。YokeOS 第一阶段对它的回答是简单截断：对话历史按 `max_history_turns` 截断，超限保留 system prompt + 最近 N 轮（[技 §4/§8]）。

**记忆压缩**解决长期记忆越存越多、检索越来越低效的问题——归并、去重、抽象、淘汰过时条目，作用在**长期记忆库**层面。YokeOS 第一阶段对它的回答是极简：归档区超 4000 字保留最近内容（[技 §5.1]），更聪明的压缩放扩展。

一句话区分：上下文压缩把现在说的话压短，管当下的窗口；记忆压缩把存下来的东西整理精简，管长期的仓库。

### 4. 记忆提炼：长期记忆能用起来的关键一步

**原始对话是啰嗦的，不提炼直接存，长期记忆库就是垃圾堆。**

提炼 = 从一段对话或一次任务里抽取值得长期记住的东西，加工成结构化、精炼的记忆条目。提炼通常靠模型自己做（读完对话输出哪些该记），也可以配合规则。提炼的质量直接决定长期记忆的质量。

这里是 YokeOS 与业界主流的一个**刻意分叉**（评审要点，二部分展开）：业界强框架普遍做**自动提炼**，YokeOS 第一阶段选择**Agent 主动调 `save_memory`**——提炼的判断权交给 ReAct 循环里的模型，时机和分区（scope）都由它显式决定，系统不自动抽取（[技 §5.1 契约三]、「第一阶段不做」清单）。

### 5. 业界方案盘点（参照课件 2026 年口径）

这块在业界已形成成熟且专业化的开源生态，按定位分类：

| 项目 | 定位 | 特点 |
|---|---|---|
| Mem0 | 即插即用的记忆层 | 最流行（47K+ star）；user/session/agent 三层作用域；向量 + 图 + 键值混合存储；自动记忆抽取；**是库不是运行时** |
| Zep / Graphiti | 时序知识图谱记忆 | 最擅长随时间变化的事实；LongMemEval 时序基准上明显领先（Graphiti 用 GPT-4o 约 63.8%，Mem0 约 49%） |
| Letta（前身 MemGPT） | 记忆即操作系统的有状态 Agent | 把记忆当 OS 管：主上下文是 RAM，归档记忆是磁盘，Agent 自己管理记忆分配；影响了整个领域 |
| Cognee | 图原生、自改进的记忆管线 | 混合图-向量-关系存储，自动化的 ECL（Extract-Cognify-Load）提炼管线，14 种检索模式 |
| LangMem | LangGraph 生态的官方记忆 | 已在用 LangGraph 就用它 |
| ReMe | 透明的文件式记忆 | 基于文件，透明可控 |

概念落地对应关系：**记忆提炼**对应各家的自动抽取能力（Cognee 的 cognify 管线）；**记忆压缩与自改进**对应 Cognee 的 memify、Letta 的自主管理；**上下文压缩**更多在 Agent 框架层，记忆框架反而管得少——它们的思路是「与其压上下文，不如把该外置的外置出去」。

一个重要判断：**LongMemEval 已成为这个领域的事实标准压力测试，不同架构在时序检索上可以差到 15 分**。这说明记忆不是有没有的问题，而是**架构选型**的问题——这正是本节评审存在的理由。

### 6. 重点解剖一：MemGPT——记忆即操作系统

**LLM 的 context window 像内存，外部存储像磁盘，MemGPT 借操作系统的虚拟内存管理来管 Agent 的记忆。**

Letta 的前身 MemGPT 值得单独讲，因为它的思想和「Agent 底座」最同源。核心洞察来自一个类比：context window 快、贵、但小；外部存储慢、便宜、几乎无限。操作系统当年用**虚拟内存**解决过一模一样的问题——分页机制在内存和磁盘之间自动换入换出。MemGPT 说：能不能像 OS 管虚拟内存那样管 LLM 的上下文。

它把记忆明确分两层：**主上下文**相当于内存，其中有一块**核心记忆**（core memory）——最重要、要一直带在身上的信息，小而精、永远在场不换出；**外部上下文**相当于磁盘，放归档记忆和完整历史，用时检索调回。

MemGPT 最精妙的一步，是**把记忆管理的控制权交给 Agent 自己**：给 Agent 一组操作自己记忆的工具（写进核心记忆、改掉过时的、归档当前上下文、从归档检索），上下文快满时给一个类似「内存压力」的信号，Agent 自己决定总结什么、归档什么、丢什么。

对 YokeOS 直接有用的两点：一是**核心记忆**这个分层概念（「永不换出的小块」）——已吸收进 `MEMORY.md` 核心分区；二是**压力触发自动整理**这个机制——留作扩展阶段候选，等出现真实信号再考虑（信号驱动原则）。另有一点对 YokeOS 尤其亲切：MemGPT 对 Agent 暴露的就是一组**稳定的记忆操作**，底层怎么换入换出是它自己的事——这正是 `MemoryService` 门面的思想同源。

### 7. 重点解剖二：Mem0——最流行的即插即用记忆层

**Mem0 把「自动抽取 + 冲突消解 + 混合存储 + 多层作用域」打包成一个库——但它是库不是运行时，是 YokeOS 该学、已集成成一档、但绝不被它取代的东西。**

三点值得解剖：

**第一，它的核心不是「存」，是「抽取与更新」。** 简单方案把对话原样 append 进记忆库；Mem0 在 `add` 时用模型提炼出该记的事实，并拿新事实与已有记忆比对：矛盾就更新、重复就合并、无关才新增。用户三月说「我用 Python」、七月说「改用 Go 了」，Mem0 倾向把旧记忆更新掉而不是让两条并存打架——**add 即消解，而非纯堆叠**，这是它区别于「往文件里追加」的分水岭。

**第二，它的分层按「作用域」切：user / session / agent 三层。** 注意这跟 YokeOS 的核心/归档是**不同的切法**——YokeOS 按「重要性与生命周期」切，Mem0 按「归属谁」切，两套维度可对照但不冲突。

**第三，底层是向量 + 图 + 键值的混合存储**，这是它比纯向量方案在关系型记忆上更强的原因。

**对 YokeOS 的评审意义有两条**：其一，Mem0 的「add 即去重更新」点破了纯 append 模式的软肋——记忆量一大，同一件事的新旧说法会并存矛盾；YokeOS 的解法是把更新责任交给 Agent（模型在 ReAct 里判断「这条改了」再调 `save_memory`），Mem0 档则是把这件事直接交给 Mem0 的消解管线——这正是三档后端里 Mem0 档的存在价值。其二，Mem0 **可自托管、是库不是运行时**，不会像 Letta 那样与 YokeOS 的运行时定位打架——所以它能以「外部集成档」进第一阶段（自托管、REST、数据不出域，[技 §5.1]）。

**同时要看清成本与边界**：自动抽取每次 `add` 多一次模型调用（成本、延迟）；冲突消解逻辑是黑盒，出错不好审计；对严监管私有部署，任何经外部管线的记忆处理都要单独评估——这正是默认档（Markdown/SQLite）选择「自己用文件/库做、Agent 手动 `save_memory`」的理由：复杂度和数据都攥在自己手里。

### 8. 重点解剖三：时序知识图谱——当「事实会随时间变化」时

**向量检索擅长「意思相近」，但不擅长「关系」和「时间」；知识图谱是这类问题的专门解法——也是 YokeOS 明确不自造、留待信号驱动的一层。**

向量检索的两个盲区是**关系**和**时序**：用户三月说「我在 A 公司」，七月说「跳槽去了 B 公司」。向量库里两条记忆都在，问「用户现在在哪工作」，语义匹配可能把过时的 A 那条也召回甚至排在前面——它只会算「哪条跟问题最像」，不知道 B 比 A 更新，也不知道「就职于」是会被后续事实推翻的关系。

Graphiti / Zep 的解法是**时序知识图谱**：实体是节点，关系是**带时间戳的边**（valid_from / valid_to）。新事实进来不覆盖旧边，而是给旧边打上「失效时间」——既保留「曾经在 A」的历史，又明确「当前在 B」。这就是它在 LongMemEval 时序基准上领先的根源。

三种存储不是替代，是各有所长：文件/键值擅长简单的「是什么」，向量擅长「意思相近」，图谱擅长「谁和谁什么关系、什么时候变的」。真正强的记忆层往往三者混合（如 Mem0）。

**对 YokeOS 的评审意义三条**：

- 它点破了核心记忆的一个长期隐患：核心记忆装「用户是谁、项目背景、关键偏好」，但这些恰恰是**会变的**。YokeOS 第一阶段把时序一致性的责任交给 Agent 的判断（主动更新而非引入图引擎）——能力上确实弱于时序 KG，换来零依赖、可控、私有可托管，是克制原则的又一次体现。
- 图的上马门槛比向量更高（图存储 + 图查询）。YokeOS 的目标场景（运维助手、每日日报这类）以「用户偏好 + 事实陈述」为主，关系密度和时序复杂度都不高，图记忆优先级低于向量——真到非上不可那天，集成可自托管方案比自造理性。
- YokeOS 的对照立场落在 [技 §9.1]：第一阶段三档都**不在进程内自建向量层**；语义检索需要时切 Mem0 档由外部服务承担，进程内向量层（LanceDB / pgvector / JVector 三选一）放扩展阶段决议。

## 二、动手前先想清楚几件事（评审要点）

评审不是复述技术方案，是拿业界方案当镜子照它。以下几件事在评审文档里必须有明确结论，其中前四件是设计立场，后六件是坑——**每个坑在第 22 节都要有一个对应的回归测试**（评审课点名，22 节 harness 承接）。

**第一，设计原则：方向想清楚，接口设计对，实现只做当下。** 三者的分界线是接口这道墙——墙之上（`MemoryService` 门面、`LongTermMemoryStore` 契约）现在就定稿，墙之下（存哪、怎么检索）只做当下需要的。不做最强的记忆系统，做够用、可控、能平滑长大的记忆系统。

**第二，术语口径定稿：两层、两分区，不照搬业界叫法。** YokeOS 的规范口径是**两层记忆**（会话 + 长期）——会话记忆即 Session（SQLite）；长期记忆内部再分**两分区**（核心 / 归档），落在 `MEMORY.md` 的两个 header 或 `memory_entries` 的 `scope` 列。参照课件与 MemGPT 讲「三层」（核心/会话/归档）是语义参照，本项目对外叙述一律用「两层两分区」——评审文档要把这条口径写死，避免 22 节实现时两套叫法混用。

**第三，为什么「Agent 手动 `save_memory`」而不是「系统自动提炼」。** 这是最容易被挑战的设计，评审要能不看文档说出依据：①自动提炼解决的问题（「重要信息容易漏记」）在第一阶段还只是推测，没有真实信号（信号驱动原则）；②ReAct 循环里 Agent 本来就能随时判断「这句该记」主动调 Tool，这条路径工程量接近零；③自动提炼要多一套「什么算会话结束/窗口快满」的判断逻辑 + 每次多一次模型调用。等真出现「用户反馈 Agent 经常忘事」的信号，自动提炼才是扩展阶段的候选项。

**第四，为什么第一阶段不上向量（也不上图）。** [技 §9.1] 已论证：LanceDB Java 本地嵌入式未 GA（当前 SDK 只支持远程 Cloud/Enterprise，不合单二进制定位）；Qdrant/Chroma/Milvus 要外部进程；pgvector 要外部 PostgreSQL；JVector 纯 Java 但成熟度待验证。第一阶段的检索 = 关键词匹配（Markdown 档行匹配、SQLite 档 `LIKE`），记忆量不大时够用。上向量的信号：关键词检索开始找不准、记忆量过千、出现跨会话精准召回的真实需求——三个信号一个都没出现之前不上，顶住「业界都上了」的焦虑。

**第五，自造 vs 集成的锚点：记忆是不是 YokeOS 的核心差异化能力。** 答案是「记忆是核心能力（能力三），但智能记忆不是第一阶段的差异化卖点」——所以：Letta 只做思想参照绝不集成（同层竞品，集成等于在 Agent OS 里塞另一个 Agent OS）；Mem0 以「自托管集成档」进入第一阶段三档（它是库、被设计为被集成、数据不出域）；进程内向量层倾向扩展阶段自造薄层或按 [技 §9.1] 三方案决议。

**第六，六个坑——评审点名、22 节钉测试。**

- **坑一：`MEMORY.md` 无限膨胀不截断。** 症状：注入超 context window。修复：归档区超 4000 字保留最近内容，**核心区永不截断**（[技 §5.1 契约二]；CLAUDE.md 陷阱表已有条目）。→ 22 节回归点：超长归档区被截、核心区一个字不少。
- **坑二：`MEMORY.md` 做缓存或预载。** 症状：`save_memory` 之后下一轮看不到新记忆。修复：契约一**每次现读不缓存**（[技 §5.3]；指南 §4.4 跑偏表已有）。→ 22 节回归点：写入后下一次组装 prompt 立即可见。
- **坑三：把 `USER.md` 当 `MEMORY.md` 写。** 症状：Agent 改掉用户的初始设定。修复：`USER.md` 用户手写、YokeOS 只读；成长记录只进 `MEMORY.md`（[技 §5.4]，来源与生命周期不同）。→ 22 节回归点：Memory 写路径碰不到 USER.md。
- **坑四：scope 由系统猜。** 症状：该进核心区的进了归档区（被截掉）或核心区被塞满。修复：契约三**Agent 经 `scope` 显式指定，系统不猜**，默认 `ARCHIVAL`（[技 §5.1]）。→ 22 节回归点：不传 scope 落归档区、传 CORE 落核心区。
- **坑五：检索或截断越界作用到核心区。** 症状：核心记忆被 `recall` 重复注入或被截断丢字。修复：契约二/四——**截断与检索都只作用归档区**，核心区靠全量注入本来就在场（[技 §5.1]）。→ 22 节回归点：`recallByKeyword` 只匹配归档区。
- **坑六：`memory_entries` 表演进走 `ddl-auto=update`。** 宪法 7 老坑的 Memory 变体。修复：手工建表脚本，与 sessions/审计表同口径（[技 §9.2]）。→ 22 节回归点：建表走 `schema.sql`。

**第七，两处文档链张力，评审必须留裁决记录。** 评审课的独有价值：把平时散着的口径冲突写成白纸黑字的裁决，22 节照裁决实现，不再各凭理解。

- **张力一（需 ↔ 技）**：[需 §5.6] 说「Agent 启动时 MEMORY.md 整个文件注入 system prompt」，[技 §5.3] 说「每次组装 prompt 现读、不缓存」。粒度不同、方向一致，**以技为准**（每次现读是「写入下一轮立即可见」的必要条件；「启动时」是需求文档的粗粒度表述）。需求文档不回改，裁决记进评审文档。
- **张力二（宪法 5 字面 ↔ 模块表落位）**：宪法 5 说「内置 Tool……合并在 `yokeos-tool` 一个模块」，而模块表把 `MemoryTools`（`save_memory`/`recall_memory` 两个内置 Tool）放在 `yokeos-memory`。解读：宪法 5 管** Tool 基础设施**的合块（`ToolRegistry`、MCP、Sandbox、Notify 与文件/Shell/HTTP 等通用内置 Tool），`MemoryTools` 是能力三的组成部分、随能力落位 `yokeos-memory`，注册进 `ToolRegistry` 与其他内置 Tool 一视同仁（[技 §5.1]）。评审文档把这条解读写死，22 节照此落位——如评审中对此解读有异议，属软门禁③（文档链冲突），停下问用户。

## 三、评审怎么做：评审文档的结构与口径

本节的产出是一份评审文档（业界对照 + 本项目设计定稿），落在 `specs/006-memory-review/`。评审方法 = **三读对照法**：逐条读技 §5 → 每个设计点对照业界方案问一句「业界怎么做、我们为什么这样/不这样」→ 落「定稿」或提「张力」。发现文档链内部冲突时**修文档优先**（软门禁③），评审文档记录裁决。

评审文档六段结构：

1. **评审范围与方法**——输入（[需 §5.6]、[技 §5/§9.1]、参照课件业界材料）、方法（三读对照法）、结论形态（定稿清单 + 差异记录 + 张力裁决 + 22 节素材要点）。
2. **业界方案对照**——两张表：概念对照（短期/长期、上下文压缩/记忆压缩、提炼、核心/归档 ↔ YokeOS 对应物）与项目对照（Mem0/Zep-Graphiti/Letta/Cognee ↔ YokeOS 采纳什么、偏离什么、为什么）。每个对照点带出处。
3. **YokeOS 设计定稿**——评审冻结清单，逐条引 [技 §5] 条款：`MemoryService` 门面（ReAct 只见一个接口）；`LongTermMemoryStore` 三方法（`append(content, scope)` / `load` / `recallByKeyword`）与**四条行为契约**（不缓存 / 核心区永不截断 / scope 显式指定 / recall 是关键词检索）；三档后端（`MarkdownMemoryStore` 默认单机档 / `SqliteMemoryStore` 结构化档 / `Mem0MemoryStore` 自托管集成档）与 `memory.backend` 配置键；`MEMORY.md` 两分区格式（`## 核心记忆` / `## 归档记忆`，每条带日期 header）；注入时机（每次组装 prompt 现读）；`USER.md` 与 `MEMORY.md` 的只读/读写边界；「第一阶段不做」清单照搬。
4. **与参照实现的差异记录**——显式列出与参照课件立场的分叉及理由：①参照阶段一纯文件 + 关键词、向量放阶段二；YokeOS 三档后端**第一阶段一次交付**（含 SQLite 档与 Mem0 集成档，但三档都不含进程内向量层——升级立场与参照一致）。②参照讲「三层记忆」；YokeOS 口径「两层两分区」。③参照把 Mem0 定位为「扩展阶段可能集成」；YokeOS 已把它定为一档进第一阶段（企业数据不出域诉求前置）。
5. **张力与遗留裁决**——至少收录二部分的张力一、张力二；评审中新发现的张力按软门禁③处理（停下问用户，修文档优先），裁决全部留痕。
6. **结论：第 22 节 specify 素材要点**——六段式骨架的预填要点（背景价值、用户场景、FR 候选、明确不做、验收标准、依赖假设），外加「坑 → 回归测试点」清单（坑一~坑六逐条），让 22 节 specify 起手就有料。

**本节交付物**（Spec-Kit 拆解锚点）：

- 评审文档：`specs/006-memory-review/review.md`（上述六段结构）
- 验收报告：`specs/006-memory-review/acceptance-report.md`
- 明确不交付：**无代码、无测试、无配置、无表**——全部归第 22 节；本节无 spec 三件套（指南 §4.2：评审节有验收报告，无 spec 三件套）
- 前序依赖（本节引用、不改动）：[技 §5] 全文、[需 §5.6]、`memory_entries` 表定义（[技 §9.2]，22 节建表）
