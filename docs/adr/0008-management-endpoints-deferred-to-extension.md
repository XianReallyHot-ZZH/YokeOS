# 管理性端点偏差：需求篇赢，定时任务与白名单管理端点列扩展规划位

参照实现窗口内交付了两组管理性端点与管理页——定时任务管理四端点（`/api/v1/schedules` 前缀的任务查询、执行历史、立即补跑、启停）加管理台"定时任务"页，以及沙箱白名单管理端点。YokeOS 需求篇的核心端点清单（18 个）与管理台页面清单均未包含它们。按「上游赢、理由写进文档」的纪律（需求分析篇拍板先例），这两组端点与对应管理页列入扩展规划位，不收进第一阶段：第一阶段的可查性由 `scheduled_tasks`/`task_executions` 落库加 Session 查询与审计两表承接，白名单走 `application.yaml` 配置形态。技术方案 §7.3/§8.5 已按此记录；未来读者对照参照库窗口末态发现缺这两组端点时，以本 ADR 为准。

## Considered Options

- **全部收进第一阶段（与参照窗口末态完全对齐）**——被拒：扩大 What 范围需回改需求篇端点表与管理台页清单，破坏「上游赢」先例；且两组端点服务的可查性与管控在第一阶段已有承接物。
- **只收定时任务四端点、白名单端点留扩展**——被拒：同样要回改需求篇，且切一半造成"定时任务可管、白名单不可管"的不对称，边界反而不清。

## Consequences

- 技术方案 §13.2 遗留未决表已挂此两项；扩展阶段启动时（尤其做审计仪表板与 Web 认证时）重新决议是否兑现。
- 第一阶段与参照库的逐节对照在此处存在一处**已声明的形态差**，属刻意保留，不是遗漏。
