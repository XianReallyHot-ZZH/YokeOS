# YokeOS AI 编程指南

> 本文档定义 YokeOS 的 AI 编程实施思路，是立项文档链的第五篇：用什么方式做——人机分工、流程选型、门禁与验收证据。主体思路是用 **Spec Kit** 完成主体开发：把已有的需求文档和技术方案喂给规格工具链，按需求文档第 11 章的节序映射（第 16~31 节）逐节实施；扩展阶段的小颗粒增量切换到手动提示词配合 Claude Code。前置阅读《YokeOS 行业调研》（`docs/IndustryResearch.md`）、《YokeOS 产品定位》（`docs/yokeos.md`）、《YokeOS 需求文档》（`docs/DemandAnalysis.md`）与《YokeOS 技术方案》（`docs/TechnicalSolution.md`）。本文档讲思路、拆解与门禁契约，不绑定具体时间安排，也不展开提示词细节。
>
> 本文档以最新技术方案为准：第一阶段交付的是 Agent 底座的单机运行时内核，Maven 模块为 9 个（技术方案第 10 章），六个核心能力作为拆解的骨架层。**喂给下游（spec、plan、宪法）的必须是最新版文档**——文档与实现脱节时，下游按旧文档生成的规格会整体走偏。

## 1. 实施总览

### 1.1 主体思路：规格驱动 + 手动提示词的双模式

YokeOS 的 AI 编程实施分两个阶段，两个阶段用不同的协作模式：

| 阶段 | 模式 | 适用场景 |
|------|------|---------|
| **主体开发阶段** | 规格驱动（Spec Kit 完整流程） | 第一阶段运行时内核，第 16~31 节逐节交付，9 个 Maven 模块 |
| **增量开发阶段** | 手动提示词 + Claude Code | 扩展阶段的功能补齐、修 bug、加 Channel 等小颗粒度增量 |

边界规则：**规格流程适合大颗粒度 greenfield，手动提示词适合小颗粒度增量**，判断标准是流程开销与工作量之比——完整走一次 constitution → specify → plan → tasks → implement 的开销大于单次任务本身时，就不该走规格流程。大 feature 例外：涉及新增 Maven 模块、修改宪法、跨多个核心能力的增量，仍走完整流程。工具选择跟工作性质匹配，不搞一刀切。

### 1.2 跟需求文档 + 技术方案的关系

实施流程不重写需求和技术方案，而是把已有文档喂给规格工具链。具体对应关系：

| 流程输入 | 来源文档 | 作用 |
|---------|---------|------|
| 节级 spec（specify）输入 | 需求文档对应节的能力主线 + 可演示成果（第 11 章节序映射表） | 转成当节的 feature spec，只含 WHAT/WHY |
| 节级 plan 输入 | 技术方案对应章节（映射表见 3.3）+ 第 10 章模块表 + 第 13 章逐节技术交付物 | 转成模块化实施 plan，只含 HOW |
| `constitution.md` | 需求文档第 3 章设计目标 + 技术方案第 1.1 节决策一~八 + 已声明的结构决策（见 3.2） | 非协商原则，凌驾于一切临时便利 |
| 节级完成判据 | 需求文档第 11 章「可演示成果」 | 每节验收的硬判据 |
| 阶段级验收 | 需求文档第 13 章验收标准 + 第 14 章两个日跑 Demo | 第一阶段收口的硬条件 |

已有文档的投入不浪费，规格工具链只负责把它们转换成 AI agent 能直接消费的格式。**喂文档前先核对版本**：技术方案是 plan 的输入，plan 里的模块结构必须跟技术方案第 10 章的 9 个模块一致——喂了旧版，生成的 plan 就按旧结构走偏。

### 1.3 拆解策略：按节拆，能力做骨架

第一阶段主体开发按**节**组织：需求文档第 11 章的节序映射表（16 节）就是实施单元清单，**节奏自定、顺序不乱、不设日历时间盒**，每节一个原子交付物。六个核心能力不作为拆解单位，而是作为**骨架层**——它们之间的依赖关系决定节序：

```
对接 LLM（16） → ReAct 循环（17） → ┌ Memory（21 评审 → 22）┐ → Web Service（26）
                                    └ 工具体系（20）────────┘
通知（19）与定时（25）是能力五的两半，分别挂在 ReAct 之后与 Web 之前；
CLI（18）是第一个可用入口；29~30 把"一个目录 = 一个 Agent"与动态管理补齐；31 收口发布。
```

- 通知与定时不是供养型能力，是出站通道和第三触发源，所以不像 Memory/Tool 那样各占连续节，而是拆在两处（19 / 25），中间夹着 Memory 与 Sandbox 的评审与实现
- 第 21、23 节是评审节（Memory、Sandbox 设计评审，不产码），评审产出作为第 22、24 节 spec 的素材——**评审产文档、文档产 spec**，不直接从评审结论跳到代码
- 第 27、28 节是串联节，不开新 spec，只把端到端链路固化为 `@Tag("integration")` 集成测试
- 第 31 节是 Demo 节，只做真实运行与发布

节序只表达依赖顺序，**不用 P1/P2/P3 之类的优先级标记**——排后的节不是可以不做的节。第 26 节 Web Service 排在 Memory/Tool 之后是因为它依赖前序全部能力就绪，恰恰它是 YokeOS 区别于偏个人定位项目的关键能力。

具体到仓库形态：每个代码节一个 spec 目录（`specs/016-provider/` … `specs/030-agent-management/`），内含 spec / plan / tasks 三件套与当节验收报告；评审节与串联节的目录只放评审文档或验收报告。

### 1.4 Spec Kit 匹配度评估

选定工具前先对照它的适用场景逐条评估，不默认适配：

| 评估维度 | YokeOS 情况 | 匹配度 |
|---------|------------|--------|
| greenfield | 从零开发的全新项目，9 个 Maven 模块 | ✅ 完全匹配 |
| 规模 | 18 个 REST 端点、9 内置 Tool、六张表、16 节交付，典型 medium 规模 | ✅ 完全匹配 |
| 需求清晰 | 已有完整立项文档链，每节有可演示成果与技术交付物 | ✅ 完全匹配 |
| AI agent 协作 | 全程 Claude Code 做主体开发 | ✅ 完全匹配 |
| 方法论沉淀 | 规格流程强制产出可追溯的规格与验收证据——过程差异化本身就是本项目的立项承诺 | ✅ 匹配 |

**结论**：Spec Kit 是主体开发的工具选择。它的社区共识短板（小改动流程过重、brownfield context 失效）对本项目分别由增量阶段双模式、纯 greenfield 性质化解。

## 2. 工具链与对照层

### 2.1 规格工具链：Spec Kit

主体开发采用 GitHub Spec Kit：`specify init` 生成 `.specify/` 工作区（constitution、spec / plan / tasks 模板与配套脚本），核心命令链是 specify → (clarify) → plan → tasks → (analyze) → implement。三条使用纪律：

1. **版本锁定**：实施前锁定一个具体的 Specify CLI 版本号，整个第一阶段不升级——工具本身迭代快，命令名、artifacts 格式、集成方式可能在版本间变化；具体命令形态以实施时官方文档为准，本文档只锁流程与门禁，不锁命令细节
2. **只用官方核心命令**，不引入社区扩展增加不确定性
3. **一次只推进一节**：每节独立的 spec 目录、独立的 feature 分支、独立的验收闭环

### 2.2 节级开发工作流

逐节实施不是裸跑命令链，而是套一层节级工作流：备料（H0 开工纪律）→ specify → clarify → plan（人工定向 review）→ tasks（固定停点）→ implement（写前/写中/写后门禁）→ 收尾（六项证据 DoD + 验收报告 + 变更总结）。门禁体系（第 5 章）全部挂在这条工作流的节点上；工作流跑顺后固化为可执行的节级开发 skill，时机在第 16 节开工前——纪律由流程的默认行为保证，不靠记忆负担（固化形态见 3.5）。

### 2.3 方法论对照层

主体流程不开第二套方法论，但设一个**对照学习层**：以业界公开的 AI 编程方法论（如 mattpocock 技能集的 grill → spec → tickets → implement 形态）作为对照轴，维护一张「作者工具链 ↔ 对照方法论」的映射表沉淀在 `docs/methodology/`；每节验收报告含「方法论对照」节（见 6.1），记录当节实践对该方法论的印证与反检。对照层不进主流程、不叠加门禁——两套门禁叠加只会增加每节流程成本，对照价值靠映射表与验收报告的一节即可获取。

## 3. 准备阶段

准备阶段是第 16 节开工前的脚手架工作，产出工程地基、宪法、节级输入映射三样，让后续每一节都在冻结的决策与就位的门禁上跑。

### 3.1 工程地基初始化

把工程地基一次性装好，业务逻辑（六个核心能力）不在这一步。交付清单：

- **Maven 九模块骨架**：`yokeos-core / provider / memory / tool / channel-cli / web / storage / cli / boot`（职责见技术方案第 10 章），`yokeos-boot` 为启动模块打 fat JAR
- **基础组件**：Logback 结构化日志（生产 JSON，禁 `System.out`）、Spring MVC + 虚拟线程、springdoc OpenAPI、统一响应体 `ApiResponse` + `GlobalExceptionHandler`、`${ENV_VAR}` 配置占位与 `ConfigLoader` 启动校验
- **质量门禁全链路**（第 5 章七件套）全部接入 `mvn verify`，pre-commit 本地把关格式，CI 跑全量
- **审计两表建表脚本预留位**（`tool_invocations` / `llm_calls`，第 16 节起写入）

验证标准：`mvn clean verify` 全绿；fat JAR 起得来；`/swagger-ui` 能打开；故意写一行不规范代码门禁要红。工程地基只装基础设施不改业务代码，与宪法、CI 的分工是：宪法钉死硬约束，CI 强制执行检查，地基把东西装上。

### 3.2 项目宪法

`constitution.md`（落 `.specify/memory/`）是项目的 **non-negotiable principles**，所有后续 spec、plan、tasks、implement 都要遵守。九条原则从需求文档设计目标、技术方案决策一~八与结构决策提炼：

| # | 原则 | 规则 | Rationale |
|---|------|------|-----------|
| 1 | **自实现 ReAct 循环** | `ReActLoop` 自己实现，不用 Spring AI 的 Agent 抽象 | Agent 的核心竞争力在运行机制本身；交出去丧失控制权 |
| 2 | **Spring AI 只用两件事** ⚠️ | 只用协议转换 + `@Tool` schema 生成；**禁用自动 tool 执行**与 eager 自动装配 | **最容易被写错的一条**——启用自动执行会导致 tool 被调两次 |
| 3 | **Provider 显式映射** | 维护 `provider name → ChatModel` 显式映射，不做容器类型扫描 | Bean 类型相同，类型扫描路由错乱 |
| 4 | **同步执行 + 虚拟线程** | 全程同步阻塞，禁引入 Reactor / WebFlux / `CompletableFuture`（调度线程池以第 25 节 `ThreadPoolTaskScheduler` 为唯一例外） | 虚拟线程已够；异步让复杂度激增 |
| 5 | **Tool 三合一** | `YokeTool` 统一抽象；内置 Tool、MCP Client、`ToolRegistry`、Sandbox、Notify 合并在 `yokeos-tool` 一个模块 | 共享同一抽象与注册表，拆开依赖混乱 |
| 6 | **Sandbox 接口先行** | 接口不携带任何一档实现特有的概念；第一阶段只填 `WhitelistSandbox`；不用 `SecurityManager`（JDK 21 已不可用） | 未来换重隔离只加实现类不改调用方 |
| 7 | **SQLite + MEMORY.md，审计 day one** | 审计两表从第 16 节起写入落库；表结构演进不走 `ddl-auto=update`（手工建表脚本） | 「日志够了」是假省——反解析返工成本更高 |
| 8 | **一个目录 = 一个 Agent** | `AGENT.md` frontmatter 派生 Profile，正文与引用 Skill 正文注入 system prompt；Skill 不进 `ToolRegistry`、不预载正文 | 配置即 Agent；Skill 是上下文资源不是可执行 Tool |
| 9 | **结构照抄，瑕疵不继承** | 九模块边界与依赖方向镜像参照实现；参照已知工程瑕疵（CLI 入口零测试）补上，不继承 | 逐节对照是第一阶段使命；照抄的是设计，不是疏漏 |

宪法治理条款：

- **写一次定下来，整个第一阶段不改**。中途发现某条原则不对，停下来重新讨论——**AI agent 不得自行修改宪法**，修改宪法属于设计变更
- 修订走显式流程：语义化版本（MAJOR 原则删除/重定义 / MINOR 新增 / PATCH 措辞），修订必须说明动机与影响，文件头维护 Sync Impact Report
- **修订必须同步所有受影响文档**——同步清单必须包含本指南与 CLAUDE.md，只改宪法不改下游文档，等于没改
- 宪法与 CLAUDE.md **双向一致**：CLAUDE.md 是宪法的运行时版，两者不得矛盾

## 4. 逐节实施

### 4.1 节级工作流（七步）

每个代码节走同一条工作流，步骤与门禁挂点：

**第 0 步 · 课型分流**：按需求文档第 11 章课型分流——代码节走完整流程；评审节（21/23）拒绝产码；串联节（27/28）与 Demo 节（31）走特殊模式（见 4.2）。

**第 1 步 · H0 开工纪律**：三读——当节需求文档行、技术方案对应章节（3.3 映射表）、前序各节交付物清单；对前序交付物逐个 grep 确认存在，缺了停下补前序，不跳步自造；确认在当节 feature 分支上（`specs/{NNN}-<slug>` 命名），不在主干上直接开发。

**第 2 步 · specify**：按六段式骨架从需求文档当节内容提炼，**只写 WHAT/WHY，不带类名与技术栈**：

```text
第{N}节需求：<模块名>——<一句话定位>
背景与价值。
用户场景。（2~3 个）
功能需求。FR1~FRn，每条可测试
明确不做（边界）。（需求文档该节「第一阶段不做」逐项照搬）
验收标准。自动化部分由验收 harness 承载；人工项单列
依赖与假设。（前序交付物；外部依赖）
```

**第 3 步 · clarify**（建议跑）：规格工具链的澄清问答回填 spec；答案只从两份上游文档找，找不到就是软门禁（见 5.2），停下问人。

**第 4 步 · plan**：输入 = 固定技术栈句（JDK 21 + Spring Boot 3.5.x + Spring AI Alibaba + SQLite + JPA；凭证走环境变量；SQLite 手工建表脚本）+ 当节模块落位（对照技术方案 §10）+ 测试策略句 + 语法禁区句（见 5.1）。**plan 生成后人工定向 review 是必要环节**，检查单见 4.4；review 通过后 plan.md 锁定。

**第 5 步 · tasks + 固定停点**：生成任务清单后自动比对「任务 ↔ 本节技术交付物」（技术方案 §13 对应行）与「测试任务先于或伴随实现任务」（验收 harness 先行），输出比对结果，**停下等人确认后才进 implement**。这是流程中唯一的固定停点，不许跳过——授权颗粒度 = 回滚颗粒度。

**第 6 步 · implement**：逐任务执行，挂三层门禁——写前（H3：第三方 API 先在本地依赖核实存在）；写中（H1/H5：只创建交付物点名的对外概念、已定字面量逐字保真、异常不吞、注释只写为什么）；写后（任务级 DoD：实现与测试一起落地，该模块测试红了当场修，不攒到最后）。

**第 7 步 · 收尾**：六项证据 DoD（见 6.1）逐项过，产出当节 `acceptance-report.md` 与对话内变更总结，然后**停止**——commit / push 由人决定。

### 4.2 课型分流

| 课型 | 节 | 处理 |
|------|----|------|
| 代码节 | 16/17/18/19/20/22/24/25/26/29/30 | 走 4.1 完整流程，产码 + spec 三件套 + 验收报告 |
| 评审节 | 21（Memory 设计）/ 23（Sandbox 设计） | **拒绝产码**。产出评审文档（业界方案对照 + 本项目设计定稿），作为下一节 specify 的素材；有验收报告，无 spec 三件套 |
| 串联节 | 27（主流程贯通）/ 28（固化集成测试） | 不开新 spec。按技术方案 §12 的关键流程做真实调用逐表对账（该留的留下、不该留的没多出来、同源一致），把对账清单固化为 `@Tag("integration")` 集成测试（28 节收尾时稳定复跑）；有验收报告 |
| Demo 节 | 31 | 真实运行与发布：两个日跑 Demo 在真实环境上线、打包发布、项目主页可访问；按需求文档 §14 场景验收，不做常规模块开发 |

### 4.3 节拆解模板与重点节

每节的拆解从三份现成材料拼装，不另写拆解文档：**核心目标** ← 需求文档 §11 当节「能力主线 / 可演示成果」；**涉及模块与技术交付物** ← 技术方案 §13 当节行 + §10 模块表；**验收** ← 可演示成果 + 验收 harness。三份材料之外出现的任何新概念，都是软门禁。

三个任务颗粒度最重的节，预先点名易错处：

- **17（ReAct 循环）**：核心循环本身数十行，工程化部分（错误处理、消息累积、迭代上限、`ProfileContext` 的 `finally` 清理）拆 2~3 个子任务；`PromptBuilder` 四段拼装逐段加。⚠️ 宪法第 2 条在此节最易被违反——Spring AI 只做协议调用与 schema 生成，tool 调用的解析与执行必须走自己的 `ToolExecutor`
- **20（Tool 体系与 MCP）**：MCP Client 建议先做 stdio transport（最常用），拆连接管理 / `tools/list` / `tool/call` / 错误恢复四个子任务；实施前先用一个最简 MCP server 测连通性。内置 Tool 补齐与 `ToolRegistry` 并行推进
- **26（Web Service 与管理台）**：任务密度最高。七个 ApiController 互不依赖可并行；Session 从内存版升级 SQLite 时小心状态迁移；管理台只调既有 REST 端点、不带独立后端逻辑；审计两表此时应有完整写入路径可查

### 4.4 实施过程中的协作模式

**`analyze` 一致性检查**：每个代码节 implement 完建议跑一次（spec + plan + tasks + 代码一致性）；跨节契约被触碰时必跑。

**AI agent 跑偏宪法时主动纠正**。本项目已知的易错点（实施中发现的追加进 CLAUDE.md 陷阱表）：

| 跑偏 | 正确做法 |
|------|---------|
| 启用 Spring AI 自动 tool 执行 | 禁用（宪法 2），tool 被调两次时先查这里 |
| ReAct 用 `ChatClient.prompt().call()` 高层抽象 | `chatModel.call` + 自己解析 tool call（宪法 1） |
| Provider 靠类型扫描区分 | 显式 `provider name → ChatModel` 映射（宪法 3） |
| 在循环/请求链路引入异步或响应式 | 同步 + 虚拟线程（宪法 4） |
| Tool 拆成多个模块 | 三合一 `yokeos-tool`（宪法 5） |
| `AGENT.md`/Agent 目录被当成 Tool 注册 | 归 `ContextLoader`：正文注入 prompt，附属资源经既有 Tool 按需取用（宪法 8） |
| 审计只写日志不落库 | 两表 day one 写入（宪法 7） |
| 表结构演进依赖 `ddl-auto=update` | 手工建表脚本（宪法 7） |
| `MEMORY.md` 做缓存或预载 | 每次现读，写入下一轮立即可见 |
| 白名单只做字符串 `normalize+startsWith` | 真实路径校验（技术方案 §6.7） |
| 钟推另开执行链或新会话概念 | 复用 `AgentService.process` 与既有 Session 公式（§8.5） |
| 模块擅自增删改名 | 宪法 9，停下报告 |

**跨节上下文回充**：隔天/隔周再入场时，先读三样——当节 spec、plan 进度标记、最近一份验收报告；长任务序列执行中段按固定触发器重读 spec + plan + 最近代码，回到规格，不凭记忆。

**commit 锚点**：AI 全程不自动 commit / push；每个任务（或每节）收尾由人落一个 commit——提交颗粒度 = 回滚颗粒度，不攒到整节结束才提交。每节一个 feature 分支，收尾（六项证据 DoD 通过）后由人合回 main，合流点重跑一次全量门禁，前序所有测试仍全绿为合流前提。

## 5. 门禁体系

### 5.1 双轨门禁

按「谁来判」分两轨，判定标准一条：这件事机器能不能判？能，做成硬门禁；不能，进软门禁清单。

| | 硬门禁 | 软门禁 |
|---|---|---|
| 谁来判 | 机器：测试、`mvn clean verify`、存在性核对 | 人：AI 停下报告，等确认放行 |
| 不过会怎样 | 构建失败 / 任务不得推进 | 流程暂停，等人拍板 |
| 防什么 | 做错了没发现 | **自作主张** |

**质量门禁全链路**（硬门禁的构成，宪法治理条款点名）：Spotless（Google 格式）+ 阿里 P3C 编码规约 + Checkstyle + SpotBugs / Find Security Bugs + PMD + OWASP Dependency-Check，全部接入 `mvn verify`；集成测试默认按 tag 排除，CI 与本地默认不跑，显式触发（见 6.3）。**测试纪律：九个模块每个都有测试覆盖，命令行入口模块不豁免**——入口逻辑是用户第一次接触 YokeOS 的地方，也是回归最频繁的地方（技术方案 §10）。**静态检查是门禁的一部分，解析失败等于构建失败**——实施中避开静态分析工具链解析不了的语法形态（如老版本 PMD/ASM 不支持的语法糖），宁可规约里禁用该写法，不给门禁开洞。人不做任何格式类 review，机器能卡的都卡住，人的注意力留给设计。CVE 扫描属慢速检查，本地默认跳过、CI 打开；扫描命中存量依赖时停下报告，不由 AI 自行升级依赖。

### 5.2 软门禁「必须停下」清单

遇到下列任一情况，立即停下、向人报告、等确认后继续，不得自行决定：

1. 需要创建本节交付物清单之外的任何对外概念（public 类型、配置键、数据表、REST 路径、Profile 字段）
2. 需要修改任何已定字面量（类名、方法签名、配置键、表列名、端点路径）
3. 两份权威文档之间冲突（不自行仲裁，文档优先、改文档再改代码）
4. 需要修改前序节交付的公共接口（当节文档明确列为「改造点」的除外）
5. 第三方 API 在本地依赖中核实不到（写前核实，核实不了不写）
6. 需要新增 plan 未列明的第三方依赖

批准必须落成文档，不能留在对话里：放行设计变更时，列出受影响文档清单并逐个确认已更新（技术方案、本指南、CLAUDE.md、必要时宪法），下一节的 H0 读到的文档里必须有这次批准。**图随文改**：受影响文档含技术方案时，其架构图一并核对——正文形态变了图不跟上，下一节 H0 读到的就是失真文档。

### 5.3 H0~H6 门禁骨架

| 门禁 | 挂点 | 管什么 |
|---|---|---|
| **H0 开工纪律** | 第 1 步 | 前置阅读 + 依赖存在性检查 + 分支确认——防上下文断裂 |
| **H1 设计保真** | 写中 | 公共概念能在权威文档找到出处；已定字面量逐字保真；文档与代码冲突时文档优先；「不做清单」与「要做清单」同等硬度——不写其功能、不留 TODO 桩、不预埋参数 |
| **H2 跨节契约** | 写中 + 合流 | 前序交付的公共接口只可使用不可修改；本次结束时前序所有测试仍全绿 |
| **H3 API 真实性** | 写前 | 第三方 API 先在本地依赖里核实存在；不新增 plan 外依赖 |
| **H4 全局不变量** | 收尾 | 见 5.4，每次交付前逐条自查 |
| **H5 实现质量** | 写中 | 异常不吞（catch 要么落审计/日志要么上抛）；单实现不建接口；注释只写为什么；命名与文档词汇一致 |
| **H6 完成定义** | 收尾 | 六项证据 DoD + 反作弊条款（6.1 / 5.5） |

### 5.4 全局不变量（H4）

「这还是不是我们那个系统」的最小判据，每次交付前逐条自查（逐条可 grep 或可测试）：

1. 涉外 IO（文件 / Shell / HTTP）执行前首行过 `Sandbox.enforce(...)`——Sandbox 就位（第 24 节）前的节留调用位并注明接线节
2. LLM 调用成败都落 `llm_calls`，工具执行成败都落 `tool_invocations`（含钟推触发、notify、Sandbox 拒绝走既有失败审计路径）
3. grep 无明文 key——凭证只走 `${ENV_VAR}` 占位与环境变量
4. `session_id` 只在 `SessionManager` 内按 channel + user + agent 拼接（钟推的 channel/user 固定 `scheduler` 也不例外）
5. 核心执行链路无 Reactor / WebFlux / `CompletableFuture` / 自建线程池（唯一例外：第 25 节 `ThreadPoolTaskScheduler`）
6. 无 Spring AI 自动工具执行路径（`ChatClient.prompt().tools(...)` 形态出现即违规）
7. 新增触发入口必须汇入 `AgentService.process`，不另开执行链——人推钟推同链路的静态形态

### 5.5 反作弊条款

不得通过删断言、`@Disabled`、放宽阈值让测试变绿。实现错了修实现；认为测试本身错了，停下报告。未全绿不得宣称完成。

## 6. 验收与证据

### 6.1 节级验收报告

每个代码节收尾产出 `specs/{NNN}-<slug>/acceptance-report.md`，六项证据缺一不可：

1. `mvn clean verify` 全绿（格式 / 规约 / 静态分析 / 安全扫描），贴关键输出；CVE 扫描以 CI 全绿为证据
2. 验收 harness 映射表里每个测试类存在且非空，关键回归测试逐个对得上号（测试方法名与文档词汇对账，中文方法名译成语义等价英文名、原文进 `@DisplayName`）
3. 本节技术交付物（技术方案 §13 对应行）逐项存在性核对（ls / grep 证据写入报告）
4. 前序所有节测试回归全绿（跨节契约证据）
5. 全局不变量（5.4）逐条自查通过
6. 收尾三件：**「门禁拦下了什么、怎么修的」**节（当节硬门禁拦截记录与修复方式——这条是过程差异化的直接证据）；**「方法论对照」**节（对照 2.3 映射表，记录当节实践的方法论印证与反检）；剩余人工项清单（真模型、真 webhook、冒烟等机器判不了的项目，明确「harness 已判卷，这几项待人工过」）

### 6.2 变更总结

与验收报告分开：验收报告落盘（给门禁核对），变更总结输出在对话里、**不另开文件**（它是给 reviewer 的导读，描述的是这一次的 diff，落盘即过期）。三段固定结构：改动点（按模块分组、每处一句动机、前序交付物被触碰的单独标出）；重点 review 清单（3~6 条按风险排序、给行级定位）；验证命令块（可直接复制执行 + 每条命令的预期结果）。

### 6.3 对账法与集成固化（27/28 节）

串联节启用运行时层的整体判据——拿一次**真实调用**逐表核对系统留下的痕迹：该留的留下了（每环节按设计应写的表 / 日志逐项核对）；不该留的没多出来（多出设计之外的痕迹说明有代码在文档之外行动）；同源一致（同一事实在多个入口的记录一致）。对账清单从技术方案 §12 关键流程生成，先手工对账一次，清单稳定后立刻固化为 `@Tag("integration")` 集成测试——从「手工对账、靠人记得」变成「一条命令可判」。集成测试默认排除，第 28 节收尾与每次合流前显式全量跑。

### 6.4 阶段验收

第一阶段收口以需求文档为准：核心功能验收清单（§13）逐项打勾，非功能指标（§8）压测验证，**两个日跑 Demo（§14）跑通是硬条件**——每日天气与每日科技日报各横串多个核心能力，都是钟推触发、都支持人推补跑验证同链路。等价交付 + `GitHub release v0.1.0` 收口后进入阶段总结（对应参照实现第 32 节形态，属第一阶段结束后的复盘，不在本文档范围）。

## 7. 增量阶段：手动提示词模式

主体开发完成后进入增量阶段，工作性质与主体阶段完全不同：

| 维度 | 主体开发（16~31 节） | 增量开发（扩展阶段起） |
|------|---------------------|----------------------|
| 任务颗粒度 | 大（每节跨模块、含建表与端点） | 小（加一个 Channel、补一个缺陷，通常 1~3 个文件） |
| 跨模块协作 | 有 | 通常无 |
| 上下文 | 从零设计 | 已有代码 |
| 宪法 / spec 的角色 | 生成依据 | 长期参考（增量仍须遵守宪法、不得破坏既有验收标准） |

增量阶段的典型工作流：认领 issue → fork / clone → Claude Code 打开项目描述改动 → 在已有代码上修改、加测试、跑通 → 提 PR → review + merge。不强制走规格流程；大 feature（新增模块、改宪法、跨核心能力）仍走完整流程。

主体阶段产出的 `constitution.md` 与各节 spec 长期保留在仓库：宪法对增量贡献者同样是非协商原则；既有 spec 的验收标准是回归底线——改某个核心能力时不得破坏它的验收 harness。`.specify/` 的模板与脚本继续服务后续大 feature。

## 8. 风险和注意事项

### 8.1 工具链风险

| 注意点 | 说明 |
|--------|------|
| **版本锁定** | Specify CLI 锁定具体版本，整个第一阶段不升级；命令名与 artifacts 格式以实施时官方文档为准 |
| **community extension 谨慎用** | 主体开发期间只用官方核心命令，不引入扩展增加不确定性 |
| **spec 不会自动跟实现同步** | AI agent 在 implement 阶段可能偏离 spec——每节收尾跑 analyze，跨节契约改动时必跑 |

### 8.2 实施过程中的常见挑战

| 挑战 | 对策 |
|------|------|
| AI agent 跑偏宪法 | 每次收尾人工检查 + analyze；跑偏案例进 CLAUDE.md 陷阱表，同一条目反复出现就升格为 review 检查单与回归测试守点 |
| 跨节上下文断裂 | H0 三读 + 再入场三读（4.4），回到规格不凭记忆 |
| 固定停点被跳过 | tasks 比对后的停点是流程中唯一强制停点，停点被跳过等于授权颗粒度失控 |
| MCP server 集成踩坑 | 第 20 节动手前先用最简 MCP server 测连通性（stdio 可能遇到进程启动失败、编码问题） |
| SQLite 表结构演进 | 首次建表用 `ddl-auto=update` 可以，后续演进必须手工脚本（宪法 7） |
| 静态分析与语言版本冲突 | 语法禁区句进每节 plan（5.1）；工具链兼容性是编码规范的一等公民 |
| Java 工程基础 | 实施前确保对 Spring Boot + Maven + JPA 有基本掌握——AI 写得快，看得懂才能 review |

## 9. 总结

YokeOS 的 AI 编程实施分两个阶段：**主体开发（规格驱动）**把需求文档 + 技术方案喂给 Spec Kit，按节序映射逐节实施——六大能力做依赖骨架、16 节做执行单元，每节一个 spec 目录、一条七步工作流、一份六项证据的验收报告；**增量阶段（手动提示词）**在已有代码上小步修改，宪法与 spec 长期有效。

四条主线贯穿：

1. **已有文档喂给工具链，不重写**——需求文档喂 specify、技术方案喂 plan、验收章节直接变完成判据、关键决策提炼成宪法；唯一的纪律是**喂最新版**
2. **宪法九条非协商**——八条来自技术方案决策，一条来自结构决策；AI 不得自改宪法，修订必须同步本指南与 CLAUDE.md
3. **门禁双轨，机器先判**——七件套全链路 + H0~H6 挂在工作流节点上；机器判不了的进「必须停下」清单，授权颗粒度 = 回滚颗粒度
4. **「做完」是证据不是感觉**——六项证据 + 门禁拦截记录 + 方法论对照 + 对账固化，每一步都能回答「为什么写、怎么验证的」

这正是本项目差异化立在过程的那条轴：可追溯的规格、验收证据与方法论沉淀，从第 16 节的第一个 commit 起就是交付物的一部分。
