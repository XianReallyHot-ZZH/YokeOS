# 技术方案骨架（立项期）

立项期技术文书的章级骨架，提炼自先行者立项技术方案的公共形态：三部分地图（底座 / 定义核心业务对象 / 整合验证）、决策表前置、接口先行、排除显式、节奏与需求篇同构。每节括号内是成文判据，写完一节对一次。目标密度：数百行级——厚度来自模块/接口/表字段/端点的穷举，不来自论证重复；发现同一段论证出现两次，删。

```md
# {项目名}技术方案

> 引言块：本文定义技术方案，回答 How。前置阅读：第一篇调研、第二篇定位、
> 第三篇需求——以需求文档定义的核心能力为骨架展开。
> 每个模块只给职责和功能说明，不展开代码细节，实现细节在研发阶段补充。
> 承接需求文档的定位判断：第一阶段交付什么、治理/终局在哪个阶段补齐。
> 文档结构提示：全文三部分——第一部分（第 1~N 章）底座；第二部分（第 N+1 章）
> 定义一个 {核心业务对象}；第三部分（后三章）整合验证。
（判据：读者看完引言块就知道 How 的粒度上限——没有代码——和三部分地图。）

# 第一部分：底座（{系统类别}内核）

## 1. 方案概述
一段定性（什么框架的单体、跑在什么运行时、核心循环自己实现还是复用、
单二进制还是多进程）+ 一句话技术栈总结。
### 1.1 关键技术决策
决策表（#/决策/选择/理由）先速览，再逐条展开；每条展开 =
选择 + 为什么（含不选什么）+ 不做什么/升级信号。
上游未决表移交的决议在表内标注来源；最易埋 bug 的使用边界单列一条。
### 1.2 整体技术栈
编号清单，版本写死到具体号；扩展阶段才用的项就地标注。
（判据：每条决策有「不选什么」；移交决议全部出现或有落点指向；
版本号精确；平台基线层面的已知技术债如实记录，不掩饰。）

## 2. 整体架构
触发源盘点（人工入口几个、自动触发几个）+ 统一入口不区分来源 +
引擎调度哪些能力块 + 存储层分工（关系型/文件系统各管什么）+
两个架构要点（进程收敛、接口解耦边缘扩展）。
### 2.1 分层视图
从上到下 3~5 层，每层一行成员清单。
### 2.2 {N}个能力之间的关系
供养型能力（给引擎供给的）逐条列；非供养型能力（触发源、出站通道、
对外门面）单独给安放说明——它们是什么的对称物/第几条路径/出口。
（判据：能力关系一句话能复述；每个能力在关系里有位置，无悬空能力。）

## 3~N. 能力章（每个核心能力一章，顺序与需求篇一致）
每章：模块组成（**模块名** + 职责段，接口给到方法级）+ 关键设计点
+ 「第一阶段不做」清单。
跨阶段演进的扩展点用接口先行小节：接口签名 + 中立性说明 +
阶段-实现-升级信号表。
（判据：模块与第 N+3 章工程结构表对得上；「不做」与需求篇扩展章对得上；
接口签名不携带任何一档实现特有的概念。）

## N+1. 支撑模块
工作区/目录初始化（结构树 + 幂等纪律）、配置与密钥加载、上下文/素材加载、
渠道接入、定时/触发、运行模式表、命令行清单……按项目裁剪。
（判据：单列成模块的要有一句「为什么单列」；幂等、缺失报错不静默、
校验失败不阻断启动这类纪律写明。）

## N+2. 数据持久化
### 选型说明
为什么不用更重的（嵌入式 vs 外部进程逐个排除）+ 扩展升级路径
（方案 A/B/C，决议时间留白）。
### 关系型数据
表清单（编号 + 一句话）+ 每张表的实体字段表；迁移机制的风险提示
（自动迁移在所选库上的已知弱项）。
### 文件系统数据
哪些数据放文件不放库，为什么（用户直编、版本跟踪、备份）。
（判据：每张表在正文其他章被提到过，无没出处的新表；审计类表标注
day one 写入；字段与需求篇数据模型章一致，本篇只做实现级补全。）

## N+3. 项目工程结构
模块表（模块名/职责）+ 跨模块契约归属与依赖方向 + 打包命令 +
测试纪律一句 + 仓库级资产（示例工作区、脚手架等）。
（判据：模块数与能力章/支撑章出现的模块一致；禁止循环依赖写明；
命令行入口模块的测试不豁免。）

# 第二部分：定义一个 {核心业务对象}（业务能力）

## N+4. 定义一个 {核心业务对象}：{定义本体} + {对外入口}
### 术语分层
底座 = 系统基础能力（第 1~N 章的一切）；{核心业务对象} = {定义本体
——一个目录/一份文件/一条配置}。两层分清楚是本章最关键的一条。
### 派生机制
底座吃的内部配置对象 ← {定义本体} 怎么派生出来，零改动复用底座。
### 公共可复用实体（如有）
公共库的位置、格式标准（兼容什么开放格式）、引用方式、边界
（它不是什么、不进哪个注册表）。
### 第一阶段路径
文件系统直放 + 运行时注册（注册方法是运行时方法而非仅启动期方法，
两条录入路径汇到同一段注册代码要明说）。
### 动态管理 API
端点清单（生成草稿不落盘、创建落盘+注册、查、改、删、无状态调用）
+ 实时监听/免重启语义 + 防目录穿越等安全注。
### 为什么这几件事要打包在一起交付
少任何一件闭环不成立，逐件点名。
（判据：定义本体一句话立宪；「为什么打包」能独立成段；对外只有
一类资源的口径贯穿。）

# 第三部分：整合与验证

## N+5. 关键流程
2~3 个每日自动运行/最高频端到端流程，逐个：场景一句、编号步骤
（每步动词开头、点到模块名）、验收要点（可判「跑没跑通」）、
涉及能力清单。
（判据：覆盖全部核心能力与全部触发源；至少一个流程演「钟推」；人工
补跑验证多入口同链路写进验收要点。）

## N+6. 实施节奏
形态与需求篇里程碑同构（节序映射/时间盒），节奏自定、顺序不乱、
不设重复的日历口径；本篇只补每单元技术交付物（新增模块组件/表/端点），
能力主线与可演示成果引需求篇对应表；审计/地基类写入从第几节起
就地写明。
### 遗留未决事项
本篇新立的开放问题表（事项/说明/决议时间）；上游移交的决议已清零
在此声明。
（判据：能力主线与可演示成果零重复抄；移交决议清零；新立未决
有决议时间。）

## N+7. 性能和可扩展性考虑
逐项论证怎么达到需求篇指标：并发模型、内存量级（给出估算式）、
存储写入压力、文件/网络 IO 量级、启动时间与对策。
（判据：需求篇每个指标有承载论证；依赖外部条件的项目标注不可控。）

## N+8. 总结
一句话技术栈核心 / 能力清单逐条一行 / 底座与 {核心业务对象} 的
边界线 / 实施节奏一句 / 存储选型 / 承接定位（扩展点预留清单）/
核心理念一段。
（判据：与第 1 章口径零漂移；核心理念一段话能独立当摘要用。）
```

两条全文判据：

- 通读一遍：每一节要么在立选型、要么在立结构、要么在立边界、要么在立节奏——需求复读、营销话术、代码片段出现即删。
- 对账四查：需求篇端点/命令/字段/指标逐条有承载物；移交决议清零且落点可查；「第一阶段不做」与需求篇扩展章逐条相容；章节间同一机制描述一致（含两处以上出现的表字段、配置键、端点清单）。
