# Feature Specification: 定时任务——Agent 到点自己干活的第三触发源（第25节）

**Feature Branch**: `specs/010-scheduler`

**Created**: 2026-09-21

**Status**: Draft

**Input**: 第25节需求（教学文档 `docs/class/025-scheduler.md` 一、二部分；task_id 派生生成已拍板——头部拍板记录①，技 §9.2 同步修订）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 到点自动发起、无人参与 (Priority: P1)

运营方给某 Agent 在 AGENT.md frontmatter 声明一条定时规则（cron 表达式 + 时区 + 到点要说的话）。进程启动后，到点时系统自动拼出该消息交给统一编排入口，Agent 跑完整循环，全程无人参与。这是"钟推"这个第三触发源存在的理由——每日天气、每日科技日报（31 节验收 Demo）没人会天天手动去问；没有它，"每日自动跑"的 Agent 根本立不起来。

**Why this priority**: 整个定时模块的核心价值——Agent 不用人喂话、到点自己干活。CLI/Web 是人推、定时任务是钟推，三者汇入同一个统一编排入口，ReAct/Tool/Provider 一个字不用改。单独实现即可交付价值：一条 cron 配置就能让 Agent 自动运行。

**Independent Test**: 单测直接调触发方法断言「消息交给了统一编排入口」「会话三元组固定 (scheduler, scheduler, Agent 名)」；人工项真等一次到点（每分钟 cron + 常驻进程，观察自动发起对话、审计有账、累计次数自增）。

**Acceptance Scenarios**:

1. **Given** 某 Agent 配了一条 cron+时区+消息的定时规则，**When** 进程启动完成注册、到达触发点，**Then** 系统自动拼出该消息交给统一编排入口，Agent 跑完整循环。
2. **Given** 一个 Agent 配了多条定时规则，**When** 启动，**Then** 每条都被独立注册、各按自己的 cron 与时区到点触发。
3. **Given** 定时规则的 cron 被修改并重启进程，**When** 下一个触发点到达，**Then** 按新时间触发——无需改代码重新编译。

---

### User Story 2 - 重叠触发直接跳过、不并发跑两份 (Priority: P2)

一次循环跑得比调度间隔还久（例如每分钟触发但上一次还没跑完）。下一个触发点到达时，不能并发再跑一份，也不排队堆积——直接跳过本次。

**Why this priority**: 与 US1 同等关键的正确性守点。定时任务天然会遇到"跑得慢于间隔"的情况；若不防重叠，同一 Agent 被并发触发多份——重复干活、重复推送、会话历史错乱。

**Independent Test**: 模拟某任务的锁已被占（上一次仍在跑），调用该任务的触发方法，断言这次没有把消息交给统一编排入口（本次被跳过）。

**Acceptance Scenarios**:

1. **Given** 某定时任务上一次触发仍在执行（其锁被占），**When** 下一个触发点到达，**Then** 本次触发直接跳过、不调用统一编排入口、不排队。
2. **Given** 某任务本次触发被跳过，**When** 上一次执行结束、再下一个触发点到达，**Then** 该次能正常触发（跳过是一次性的、不影响后续）。

---

### User Story 3 - 单次失败被隔离、留痕、不留死锁 (Priority: P3)

某次定时触发中途跑挂了。不能把整个调度器带崩，也不能悄悄失败什么都不留——得跟人推触发的失败一样走既有审计；且不影响这个任务的下一次触发和其它任务；无论成败，占用的锁都要释放，不留死锁。

**Why this priority**: 定时任务无人值守，失败若把调度器带崩或悄悄吞掉，会让所有 Agent 的自动运行集体停摆且无人察觉。失败隔离 + 留痕 + 不死锁是无人值守场景的生命线。

**Independent Test**: 让统一编排入口在被调用时抛异常，调用触发方法断言：不外抛（调度器不死）；紧接着再触发一次能正常进入（"二进宫"证明锁在 finally 已释放、没永久卡死）；执行历史记了一条失败记录。

**Acceptance Scenarios**:

1. **Given** 某次触发中统一编排入口抛异常，**When** 该次触发执行，**Then** 异常不外抛、调度器不崩、失败被记录（执行历史一条 success=false）。
2. **Given** 上一次触发因异常失败，**When** 下一个触发点到达再次触发，**Then** 能正常进入执行（证明失败那次的锁已在 finally 释放）。
3. **Given** 某次触发失败，**When** 事后查审计，**Then** 这次失败的调用像人推触发的失败一样留在既有审计链路里（不为钟推单开审计逻辑）。

---

### User Story 4 - 任务状态与执行历史落库可查，重启不丢 (Priority: P4)

"到点没跑、跑了什么、结果如何"要有据可查：每次执行（成功失败都）写一条历史，任务行记运行状态（上次触发、上次结果、累计次数、下次触发时刻）；重启后已登记的任务保留启用状态与累计次数。

**Why this priority**: 需求文档 §11 当节可演示成果「Agent 按 cron 到点自跑，**执行历史可查**」的后半句——可查性不推迟到后节交付（本节一次性交付参照两节的内容：调度层 + 状态落库）。第一阶段无管理端点，"可查"由两张表落库 + 钟推会话 + 审计表承接。

**Independent Test**: 幂等登记与执行历史读写的存储层单测（真 SQLite）；端到端：常驻上下文启动即登记 → 手动补跑一次 → 两表对账（历史一条成功、run_count=1、last_status=success）。

**Acceptance Scenarios**:

1. **Given** 带 schedules 的 Agent 启动，**When** 注册完成，**Then** scheduled_tasks 有该任务登记行（默认启用、累计 0）。
2. **Given** 某任务执行了一次（无论成败），**When** 查执行历史，**Then** task_executions 恰多一条且任务行状态更新。
3. **Given** 任务已登记且执行过若干次后进程重启（定义未变），**When** 重新注册，**Then** 启用状态与累计次数被保留、不被登记冲掉。

### Edge Cases

- **非法 cron / 非法时区字符串**：某条规则解析失败 MUST NOT 拖垮其它合法规则的注册与运行（单条隔离，记日志跳过）；下次触发时刻计算失败返回空、不影响本次执行。
- **时区缺省**：未显式写时区时回退服务器系统时区，但配置能显式覆盖是硬需求。
- **无任何定时规则**：所有 Agent 都没配 schedules 时，注册过程正常空跑、不报错。
- **进程退出**：调度线程 MUST NOT 阻止一次性命令（如交互对话）跑完后进程正常退出（daemon 线程）。
- **停用的任务到点**：跳过且不记执行历史（停用语义区别于失败）。
- **未登记的任务查启用状态**：按启用处理（fail-open——登记滞后不该让任务漏跑）。
- **执行记录落库自身失败**：执行已经发生，只记日志不外抛，不把调度线程搞挂。
- **文件里已删除的任务**：表内留档不删（保执行历史关联完整，孤儿行无害——重启后按文件协调时不会注册它）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供调度层，启动时扫描所有 Agent 配置里声明的定时规则，逐条注册到系统的调度能力上；触发规则 MUST 来自配置，MUST NOT 编译期写死（不用 @Scheduled 注解——给 Agent 加/改定时不应要求改代码重新编译）。
- **FR-002**: 每条定时规则 MUST 支持 cron 表达式与显式时区；时区 MUST 能在配置里指定，MUST NOT 全由服务器系统时区替用户做主（配置缺省或空白才回退系统时区）。
- **FR-003**: 到点触发时，本模块的唯一职责 MUST 是"拼一条消息交给统一编排入口"；消息内容由 Agent 配置决定、交上去之后怎么处理由既有循环负责——这两件都 MUST NOT 由本模块承担。
- **FR-004**: 系统 MUST 用按任务标识维度的进程内本地锁防重叠：上一次还没跑完、本次触发点到达时 MUST 直接跳过（不排队、不并行跑两份）；MUST NOT 引入分布式锁（第一阶段单实例）。
- **FR-005**: 单次触发失败 MUST 只记日志、不外抛、不拖垮调度器、不影响其它任务与下次触发；失败的调用 MUST 仍走既有完整审计（与人推触发的失败无区别，不为钟推单开审计逻辑）；执行结果成功失败都 MUST 写执行历史并更新任务状态；无论成败占用的锁 MUST 在 finally 释放；执行记录落库自身失败 MUST 只记日志不外抛。
- **FR-006**: 钟推也要落会话——会话身份 MUST 固定为三元组（channel=scheduler、user=scheduler、profile=该 Agent 名）；同一 Agent 的历次定时触发 MUST 复用同一会话，对话历史自然累积、靠既有最大历史轮数截断兜底；MUST NOT 为钟推新设任何会话概念；会话标识生成 MUST 沿用既有三元组公式单点。
- **FR-007**: 单条定时规则非法（cron/时区解析失败）MUST NOT 拖垮其它合法规则的注册与运行，坏规则记日志跳过；下次触发时刻计算失败返回空、不影响本次执行。
- **FR-008**: 任务状态与执行历史 MUST 落 SQLite 两张表（scheduled_tasks 存登记信息与运行状态、task_executions 存每次执行历史，成功失败都记；手工建表脚本，不走 ddl-auto=update）：注册时幂等登记——已存在则只更新定义字段（cron/时区/消息/下次触发时刻），保留启用状态与累计触发次数（重启不丢）；每次执行写一条历史并更新任务状态（上次触发时刻/上次结果/累计次数/下次触发时刻）；定义源仍是 frontmatter，两表只存"状态 + 历史"，不作为定义源；文件里已删除的任务表内留档不删。
- **FR-009**: 停用的任务到点 MUST 跳过且不记执行；未登记的任务 MUST 按启用处理（fail-open）。
- **FR-010**: 任务标识 MUST 派生生成：`{profileName}#{声明序号}`（同 profile 内按声明顺序唯一、跨 profile 前缀隔离）；frontmatter 保持三字段（cron + 时区 + 消息）不加 id 字段（拍板①）。
- **FR-011**: 调度线程池 MUST 设 daemon 线程——一次性命令（如交互对话）跑完后进程能正常退出。
- **FR-012**: MUST 保留按任务标识立即执行一次的类级方法（人推补跑入口，无视启用状态），第一阶段 MUST NOT 挂 REST 端点（调度管理端点显式列扩展规划位）。

**明确不做（边界）**: 分布式调度（选主、分布式锁、租约——多实例协调放扩展阶段）；失败自动重试、失败多次自动告警（做到"失败不崩、留痕可查"即够）；调度管理 REST 端点与管理台页面（显式列扩展规划位，第一阶段"可查"由两张表落库 + 钟推会话 + 审计表承接）；cron 表达式高级语法扩展（Quartz 级，Spring 标准 cron 够用）；交互对话模式下的调度排除开关（chat 与 serve/gateway 共用同一运行时装配，daemon 线程保证可退出——与参照行为一致）。

### Key Entities

- **定时规则（既有配置载体）**：一条定时任务的声明，含 cron 表达式、时区、到点要发给 Agent 的消息；已由前序节建全（frontmatter 三字段），本模块只消费。
- **任务标识（派生）**：`{profileName}#{声明序号}`——锁维度、表主键、执行历史关联、补跑入口查找共用的键。
- **调度层**：启动时把每条定时规则注册进系统调度能力；到点触发时按任务标识拿锁、拼消息、交给统一编排入口、失败记日志、finally 放锁。持有"任务标识→锁"的进程内表与"任务标识→可注销句柄"的表（句柄为后节运行时注销留位）。
- **任务状态（scheduled_tasks）**：登记信息（归属 Agent、cron、时区、消息）与运行状态（启用、下次触发、上次触发、上次结果、累计次数、更新时间）；定义源是 frontmatter，本表只存"状态 + 历史"。
- **执行历史（task_executions）**：每次执行一条（关联任务标识、所用钟推会话、开始时间、成败、失败信息、耗时），成功失败都记。
- **持久化契约**：登记（幂等）/记执行/查启用/启停/列表/查历史六个方法的接口，接口归核心模块、JPA 实现归存储模块（依赖倒置）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一条 cron+时区+消息的定时规则，到点即自动发起一次完整调用、无需任何人参与——自动化 harness 断言"注册参数含配置的 cron 与时区（时区以固定触发上下文下的下次触发时刻证明）""触发即交给统一编排入口"；人工项真等一次到点验证 cron 链路。
- **SC-002**: 上一次未跑完时，本次触发 100% 被跳过（0 并发第二份）——harness 恒绿。
- **SC-003**: 单次执行失败：0 次外抛（调度器不死）、执行历史恰多一条失败记录、紧接的下一次触发能正常进入（锁释放证明）。
- **SC-004**: 同一 Agent 历次定时触发的会话标识 100% 一致且符合三元组公式（channel=user=scheduler）。
- **SC-005**: 每次执行后两表对账：执行历史恰多一行、任务行的上次触发/上次结果/累计次数/下次触发时刻同步更新；重启（定义未变）后启用状态与累计次数保留。
- **SC-006**: 单条非法规则（cron/时区）导致的注册损失限于该条（其它条 100% 照常注册）。
- **SC-007**: 带交互对话的一次性命令跑完后进程正常退出（daemon 调度线程不挂住 JVM）。

## Assumptions

- 第一阶段单实例部署：进程内锁足够防重叠，分布式协调（任务归属实例协商）放扩展阶段。
- frontmatter 三字段（cron + 时区 + 消息）为已定稿配置形态（16 节），本节零 Profile 改动；任务标识派生生成（拍板①）。
- 前序交付物已核存在：Profile 的 schedules 解析、ProfileRegistry、统一编排入口 process(会话, 消息)、SessionManager.getOrCreate(三元组)、常驻命令骨架（serve/gateway，留位注释待兑现）。
- 零新增第三方依赖：调度用 Spring 自带 TaskScheduler 体系（既有传递件）；调度线程池是宪法「全程同步」条款的唯一明文例外，触发线程之外的执行链路仍纯同步阻塞。
- 「可查」在第一阶段的形态是数据库表落库（无管理端点）——排障直接查表，REST 查询端点扩展阶段补。
- 交互对话模式（chat）与常驻模式共用同一运行时装配：chat 会话期间到点的任务也会真触发一次（与参照行为一致），由 daemon 线程保证 chat 跑完可退出。
