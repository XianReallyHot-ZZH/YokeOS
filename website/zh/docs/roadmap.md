# 路线图

***开发理念：慢就是快，克制且聚焦。先把单机的运行时内核做扎实，让一个节点上运行和管理一群 Agent 这件事真正可用，再在它之上逐步生长出分布式能力。***

## 三阶段

### 阶段一（当前）：单机运行时内核

- 与参照实现对齐的完整运行时内核：[对接 LLM](./provider)、[自实现 ReAct](./react-loop)、[两层记忆](./memory)、[工具与沙箱](./tool-sandbox)、[通知与定时](./notify)、[REST API 与 Web 管理台](./web-service)
- [一个目录 = 一个 Agent](./agent)、动态管理、多 Agent 并存、打包发布
- 审计落库与白名单沙箱从第一天就在

第一阶段不追求产品功能差异化：以被验证过的参照实现为基准逐节交付、等价验收，把工程过程本身做扎实，产品层面的分叉留给有真实使用判断之后。实施按参照公开构建过程的课程节序组织（第 16→31 节），**节奏自定、顺序不乱**，不设日历时间盒，每节以「可演示成果」为完成判据——见[快速开始](./quick-start#里程碑目标清单)的节序表。

### 阶段二（规划）：能力补齐与底座分布式

- **知识库与语义记忆**：文档导入、切分、向量化检索，补齐能力版图
- **底座分布式**：节点无状态化、状态外置（会话、记忆、审计、配置分路外置）、多副本部署，支撑更大规模与高可用
- **平台基线升级**：Spring Boot 4 + Spring AI 2.0——第一阶段锁定 3.5.x 是与参照实现逐节可比的刻意选择，如实记为已知技术债，升级作为一次真实的架构升级练习

从「一个部门试点」走向「服务全公司」时，单机会撞到三件事：扛不住量、扛不住故障、扛不住规模化治理。演进的核心原则是**实例无状态、状态外置**——这在第一阶段的架构里已经预留：实例只做「接消息、调模型、跑工具、读写外置状态」。

### 阶段三（愿景）：跨节点 Agent 协作

- 引入 Agent 通信底座，对接 A2A（2026-03 已发布 v1.0 稳定规范）
- 让多节点上的 Agent 跨节点发现、委托、可靠异步协同

### 横向能力（伴随各阶段逐步补齐）

多租户、SSO、分级审批（HITL）、完整审计与工具策略、可观测、Web 管理增强。

> 这一层是 YokeOS 区别于个人级 Agent OS 的差异化所在：[对外服务](./web-service)页里显式列为扩展规划位的管理性端点（定时任务管理、白名单管理），在扩展阶段随审计仪表板与 Web 认证一起重新决议。

## 不做什么

- **不做可视化 workflow 编排**：编排平台（Dify 等）可以作为客户端跑在 YokeOS 之上，两者互补
- **第一阶段不做**：fallback 与 hedge racing、SSE 流式、认证与 RBAC、容器级沙箱、知识库、多租户——每一项都有明确的承接位置，见各能力页的「第一阶段边界」
- **不锚概念**：路线图锚在企业刚需（私有、可控、可审计、与 Java 体系对齐）上，不锚在可能被稀释或改名的品类名词上

## 交付纪律

- 每节一个原子交付物；课型分流：代码课走完整规格流程并产码、评审课只做设计评审不产码、串联课不开新规格只固化端到端验证、Demo 课做真实运行与发布
- 某一节完不成时，立刻把末段功能挪到扩展功能，保证每节都有可演示成果
- 审计两表（`tool_invocations`、`llm_calls`）从第一个有 LLM 调用和 Tool 调用的节起就写入，不以「日志够了」为由推迟
