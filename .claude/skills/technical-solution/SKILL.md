# 技术方案（立项文档链第四篇）

帮用户把需求承诺翻译成一份 How 级技术文书：用什么做、怎么分层、每个模块管什么、数据落在哪、按什么节奏交付。它是需求文书的直接下游、研发实施与 AI 编程指南（第五篇）的直接上游——不是需求篇的复读，不是代码，也不是编码纪律书，那分别是链内第三篇和第五篇的事。

用户此刻通常在构思规划期：手里有需求篇（甚至只有一份能力承诺与选型意向），没有代码、没有实现反馈。默认路径只依赖需求输入与用户拍板；凡是依赖既有资产或参照仓库的步骤，先确认存在才走。

三条铁律贯穿全程：

1. **未拍板不动笔**。移交决议的取舍、模块划分形态、范围裁决、节奏形态是用户的决策；拍板前只出提纲和输入清单，正文一字不写。
2. **How 逐条指得上 What**。需求篇的每个端点、命令、字段、指标、验收项，在本篇都要有承载物；反过来，本篇不得悄悄做需求篇排除的东西。**上游已锁的选型（含与先行者对齐的既定决策）引用不推翻**——要偏离必须显式拍板，默认上游赢且理由写进文档。
3. **需求篇未决事项表是本篇的法定输入**。表中「决议时间 = 技术方案阶段」的条目是必答题，全部要在本篇落定；落定结果写进正文相应章节，仍开放的事项进遗留未决表并注明决议时间。移交事项悬着不接，是本 skill 的事故高发区。

## 第 0 步 · 拍板（口径）

完成判据：四个口径问题用户给出明确答案，缺一个不进第 1 步。

1. **上游输入**：第三篇需求在手吗？它的未决事项表里有多少项移交本篇？逐项清点成必答清单。只有需求、没有定位/调研，但用户有明确能力清单与选型意向：列为输入，显式标注「未经完整链固化」。
2. **范围对齐**：第一阶段边界沿用需求篇的范围基准（本篇不重定范围）；「扩展阶段」是需求篇扩展章的实现承接，本篇不为它新立产品范围。
3. **形态参照**：有先行者的技术方案可对照吗？拿得到原文与演化史吗（仓库提交历史）？拿得到则第 1 步加走考古支线；拿不到则降级为公开资料对照，缺的说明即可；没有则直接用 references/doc-structure.md 的通用骨架。
4. **落点与分界**：技术方案落在哪、给谁看（实施与第五篇的直接依据？）。与第五篇 AI 编程指南的分界拍一下：本篇立「设计与选型」（架构、接口、数据、节奏），指南立「编码纪律与过程约束」（原则条款、门禁、流程）——同一原则两篇都出现时，本篇写设计语义。

## 第 1 步 · 输入提炼（有形态参照加考古支线）

**通用部分**——把需求输入提炼成五类清单，交用户过目：

- **能力骨架**：需求篇核心能力清单，逐条列出——本篇章节的骨架；非供养型能力（触发源、出站通道这类）单独标注，第 2 步要给它们安放说明。
- **必答清单**：需求篇未决事项表移交本篇的开放决策，逐条列候选与取舍维度（含上游已锁决策构成的默认约束）。
- **粒度承诺**：需求篇的端点表、命令表、数据字段、指标数值——How 层必须逐条承载的硬约束，第 4 步逐项对账。
- **边界与排除**：需求篇全部「第一阶段不做」清单——本篇「不做」的底线，不得悄悄做。
- **既定决策**：上游文档与 ADR 已锁的选型/口径，本篇引用不推翻；需要偏离的攒进第 2 步显式拍板。

**考古支线（仅拿得到参照技术方案原文时走）**：

- 挖立项期首版：`git log --follow` 找参照技术方案的最早提交，`git show <hash>:<path>` 读原文，再读立项期末版与现版，对比结构与形态。
- 三层提取：**骨架层**（三部分结构、关键决策表形态、能力章顺序——可抄）；**粒度层**（模块职责段、接口签名、配置键、表字段、端点口径的写法——可抄）；**决策层**（具体选型与拍板理由——跟参照的项目走，不照抄）。
- **落差检测（本支线独有的价值）**：拿参照文档对照参照的**实际交付**（specs、代码、里程碑记录），列出「文档标签 ≠ 交付事实」的点——某能力文档标扩展、实际核心窗口就交付了；某章与另一章互相矛盾；某节仍写已被推翻的旧形态。文档与实现的关系有两类样本：逐节同步型与滞后补账型，两类都会留下节内失真。**自己的第一阶段范围以交付事实核对、以自己需求篇为准，不以参照文档标签为准**；对照结论只进自己的范围拍板，正文不评价参照文档质量（产品口径）。
- 可学处与反面教材一起总结；「关键原则的写入」与「关键原则的措辞打磨」是两类动作，前者是决策、后者是修订，别混。

完成判据：五类输入清单（+ 考古三层表与落差点清单）交用户过目；与需求篇矛盾或缺位的事实回报用户，不自行吸收。

## 第 2 步 · 框架拷问

拍板点用选择题（AskUserQuestion）逐个过，未拍板不动笔：

1. **移交决议逐条拍板**：必答清单每项给候选、推荐与理由。推荐项优先引用两类依据——上游已锁决策、先行者已验证的组合；上游已直接锁定的按「上游赢」确认，但确认也要落笔，不能因为「显然」就不写。决议落点（哪一章哪一节）当场指明。
2. **关键决策表对账**：本篇新立的每个关键选型都要能回答「不选什么、为什么」；最易埋 bug 的使用边界单列一条决策，坑位前置。与上游既定决策的冲突处逐条显式拍板（默认上游赢、理由写进文档）。
3. **模块划分形态**：模块清单与依赖方向（沿用先行者 / 自定 / 混合）；跨模块契约归属（依赖倒置：契约放上游模块、实现放下游）；结构照抄类决策要附「已知瑕疵不继承清单」，瑕疵与设计分得清。
4. **范围裁决逐条拍板**：先行者在对应窗口内交付了、但自己需求篇未覆盖的能力（考古支线落差检测的产出），逐条选择题——需求篇赢（进扩展规划位，正文记显式偏差及理由）/ 显式偏差收进第一阶段（需求篇要回头补账，成本当场说明）/ 折中。默认需求篇赢，不默认扩。
5. **实施节奏形态**：与需求篇里程碑同构（节序映射或时间盒）；本篇只补「每单元的技术交付物」层（新增模块组件、表、端点），能力主线与可演示成果引需求篇不重复抄。

完成判据：全部拍板点有明确答案，移交决议清零。

## 第 3 步 · 成文

按 [doc-structure.md](references/doc-structure.md) 的骨架成文。四条写作纪律：

- **How 的粒度上下限**：下限是模块职责、接口签名、配置键、表字段、端点口径——实施者能直接接走；上限是「不写代码」——「代码层面的实现细节在研发阶段补充」这句话本身就是粒度声明。
- **决策三段式**：每个关键决策 = 选择 + 为什么（含不选什么）+ 不做什么/升级信号。跨阶段演进的扩展点走**接口先行**：签名表达意图、不携带任何一档实现特有的概念；校验法是拿最重的未来实现反向套签名，能干净套入才算中立。
- **排除与纳入同样明确**：每个能力章带「第一阶段不做」；需求篇的「不做」逐条相容；范围裁决出的显式偏差在正文留理由与去向（扩展规划位），不消失也不混入核心。
- **产品口径**：过程型、学习型元语境（跟拍、对照学习、复盘）不进正文；参照与先行者可事实性引用（已验证的组合、公开的交付窗口），不以学习作业形态写。

## 第 4 步 · 对账自检

写完逐项过，任何一项不过就改文，不带病交付：

- **上游承载**：需求篇每个端点/命令/字段/指标在正文有承载物；移交决议全部落定且落点可查；术语与需求篇术语表严格一致。
- **决策完备**：关键决策表每条有「不选什么」；与上游冲突处有显式拍板记录；上游已锁选型无一处被悄悄更换。
- **粒度下限**：模块表、接口签名、配置键、表字段、端点清单到位；全文无代码。
- **节间一致**：同一机制在不同章的描述对得上（一章改了形态另一章要跟上）；「第一阶段 / 扩展阶段」标签全文一致；工程结构章的模块数与能力章出现的模块一致。
- **偏差复核**：拍板过的每处显式偏差都在正文留了理由；落差检测产出的失真点没有一条被无意识照抄或无视。
- **验收对齐**：实施节奏每单元的完成判据引需求篇验收，不另立口径；端到端流程覆盖全部核心能力与触发源。

完成判据：六项全过。

## 第 5 步 · 沉淀

- 移交决议与显式偏差若同时满足三条——难逆、无上下文会困惑、真实取舍——记一条 ADR；与先行者对齐/偏离的拍板通常够第三条。
- 遗留未决表交接给下游：实施阶段的开放问题、第五篇要固化的原则条款，逐项注明决议时间或承接位置。
- 成文或对账中发现与需求篇冲突：停下来报告用户，既不擅自改上游也不硬写。
