# 企业级 AI 编程方法论：Spec-Driven Development 与门禁体系

> **来源**：从 `vendors/oryxos` 示范工程（一个用 Spec-Kit + Claude Code 逐节开发出来的 Java 21 Agent OS，约 212 个 Java 文件、11 个特性 spec、30+ 节课件驱动开发）中提炼。
> **用法**：本文档已去掉项目专有名词，保留机制骨架与可抄模板，可作为任意 AI 辅助开发项目的方法论底座。原始材料索引见 §5。
> **提炼日期**：2026-08-23

---

## 0. 这套方法论解决什么问题

把执行交给 AI 之后，真正的风险不是"写错"——写错测试能抓。真正的风险是：

> **每一步局部合理、整体漂移**——最后交付出来的不是设计中的那个系统。

漂移有四种典型形态，这个分类本身是整套方法论的地基：

| 漂移形态 | 表现 | 为什么危险 |
|---|---|---|
| **发明** | 造出文档里不存在的公共类、配置项、端点 | 单看都"挺合理"，累积起来系统长歪 |
| **顺手优化** | 把已定签名"改进"一下、配置键换个"更好"的名字 | 下一步按文档喂料时全部对不上 |
| **提前实现** | 把"先别做"清单里的东西顺手做了 | 复杂度背上身，还没有信号支撑 |
| **臆造 API** | 写出根本不存在的第三方方法 | 编译期炸算好的，更糟的是碰巧存在但语义不同 |

所有后续机制（宪法、门禁、验收 harness、证据化完成定义）都是围绕防这四种漂移设计的。

## 1. 总纲

一句话：

> **SDD 给目标，Harness 给边界，Loop 给可控执行。**

| 层 | 载体 | 回答的问题 |
|---|---|---|
| **SDD**（Spec-Driven Development） | constitution → specify → clarify → plan → tasks → analyze → implement | 要做什么、不做什么、按什么顺序 |
| **Harness** | 测试套件 + 静态检查 + 门禁条款 | 做出来的对不对、过程越没越界 |
| **Loop** | 可执行的工作流（skill / 脚本 / 命令序列） | 每一步可控、可停、可回退 |

权力分配原则：

> **AI 可以执行一切，但改变设计的权力永远不下放。**

落到操作上是一句分野，也是整套门禁的划分标准：

> **能机器判的绝不留给人，机器判不了的绝不自行发挥。**

## 2. 十项可迁移资产

### 2.1 宪法机制：把"不可协商"变成有治理的文档

**是什么**：项目开工前，从技术方案的关键决策中提炼一份 constitution（非协商原则集），凌驾于一切个人偏好与临时便利。

**为什么有效**：AI（和新成员）对"为什么这么定"没有上下文，只给规则会形式化遵守甚至"合理化绕过"；带上 rationale 的原则才能在边界情形下做出正确判断。

**关键做法**：

- 每条原则 = 规则 + **Rationale**（违反了会发生什么具体坏事，如"启用自动工具执行会导致工具被调两次"）
- **显式标注"最容易被写错的一条"**——不平均用力，把已知高频违规点标红
- **语义化版本 + 修订治理**：MAJOR（原则删除/重定义）/ MINOR（新增原则）/ PATCH（澄清措辞）；修订必须走 PR、说明动机与影响、**同步更新所有受影响的模板和指南**；文件头维护 Sync Impact Report
- **AI 不得自改宪法**——修改宪法属于设计变更，永远走软门禁（停下报告）
- 宪法与项目级 AI 指南（CLAUDE.md / AGENTS.md）保持**双向一致**：指南以宪法为准，两者不得矛盾

**怎么迁移**：任何项目 AI 开发开工前先写。提炼来源不是编码规范（那些交给工具，见 §2.10），而是**架构边界决策**——重点是那些"AI 很容易顺手做错"的地方。8 条左右为宜，超过 15 条说明还没想清哪些真正不可协商。

### 2.2 硬/软双轨门禁 + "必须停下"清单

**是什么**：按"谁来判"把门禁分成两轨：

| | 硬门禁 | 软门禁 |
|---|---|---|
| 谁来判 | 机器（测试、构建、静态检查、脚本核对） | 人（AI 停下报告，等确认放行） |
| 不过会怎样 | 构建失败 / 任务不得推进 | 流程暂停，等人拍板 |
| 管什么 | 结果可自动验证的事 | 需要判断的事（设计变更、文档冲突、范围调整） |
| 防的失败模式 | 做错了没发现 | **自作主张** |

**核心是软门禁的触发清单**——把"AI 什么时候必须停下来问"从模糊的品行要求变成可枚举、可执行的条件：

```markdown
遇到下列任一情况，立即停下、向用户报告、等确认后继续，不得自行决定：
1. 需要创建交付物清单之外的任何对外概念（public 类型、配置键、数据表、API 路径、Profile 字段）；
2. 需要修改任何已定字面量（类名、方法签名、配置键、表列名、端点路径）；
3. 两份权威文档之间冲突（不自行仲裁）；
4. 需要修改前序交付的公共接口（当前特性文档明确列为"改造点"的除外）；
5. 第三方 API 在本地依赖中核实不到（写前核实，核实不了不写）；
6. 需要新增 plan 未列明的第三方依赖。
```

**怎么迁移**：清单直接抄走，按项目调整条目。判定标准就一条——这件事机器能不能判？能，做成硬门禁；不能，进停下清单。

### 2.3 H0–H6 门禁骨架（最值得整体抄走的表）

**是什么**：把门禁按"挂在流程哪个位置"组织成七道关卡：

| 门禁 | 管什么 | 核心条款 | 防什么 |
|---|---|---|---|
| **H0 开工纪律** | 前置阅读 + **依赖存在性检查** | 动手前必读：当次特性文档全文、技术方案对应章节、前序各次交付物清单；对前序交付物逐个 grep 确认存在，缺了停下补前序，不许跳步自造 | 上下文断裂 |
| **H1 设计保真** | 唯一权威设计源 | 每个公共概念必须能在权威文档找到出处；公共概念白名单制——交付物清单之外的对外概念一律停下报告；已定字面量逐字保真，禁止顺手改进；**"不做清单"与"要做清单"同等硬度**（不写其功能、不留 TODO 桩、不预埋参数） | 发明 / 顺手优化 / 提前实现 |
| **H2 跨阶段契约** | 前序交付的公共接口 | 只可使用不可修改（文档明确列为"改造点"的除外）；本次结束时**前序所有测试必须仍全绿**；需要前序未交付的能力时停下报告，不就地自造替代品 | 破坏契约 |
| **H3 API 真实性** | 第三方 API | 编写前先在本地依赖里核实存在（`dependency:tree`、翻 jar 源码）；不新增 plan 未列明的依赖 | 臆造 API |
| **H4 全局不变量** | 整体性判据 | 从宪法和反复钉的设计中提炼 N 条"无论做哪个特性永远成立"的不变量，**每次交付前逐条自查** | 整体漂移 |
| **H5 实现质量** | 代码内纪律 | 异常不吞（每个 catch 要么落审计/日志要么上抛）；不过度设计（单实现不建接口）；注释只写"为什么"；命名与文档词汇一致 | 过度工程 |
| **H6 完成定义** | 收口 | 证据化 DoD + 反作弊条款（见 §2.5） | 虚假完成 |

**H4 全局不变量**值得单独说：它是"这还是不是我们那个系统"的**最小判据**——比如"每次外部调用成败都落审计表"、"凭证只走环境变量，grep 无明文 key"、"全程同步阻塞，出现异步框架即违规"。条数少（5~8 条）、逐条可 grep 或可测试、每次交付前过一遍。这是对"局部合理整体漂移"最直接的一味药。

**怎么迁移**：整表抄走，H4 的不变量必须自己提炼（见 §3）。

### 2.4 验收即代码（Acceptance Harness）

**是什么**：每个特性的验收标准分两层——

- **自动化层 = 具体到测试类名和守点的测试套件**，写进特性文档，`mvn test`（或等价命令）全绿即"机器判卷"通过
- **人工层 = "做完怎么验"清单**，只放机器判不了的项目（如真实冒烟、依赖确认）

**核心纪律**：

> **"想清楚"阶段点过名的每个坑，都有一个回归测试把它永久钉死。**

坑不再依赖人的记忆，变成二进制的存在性。配套的两个习惯：

- spec 里每个 User Story 带 **Independent Test**——不依赖其他故事就能独立验证的测试设计（"注入一个注册失败，核对已写的目录被回滚"）
- tasks 里测试任务可并行标记 `[P]`，且**测试先于实现**（"T005 写测试 → T006 实现，让 T005 转绿"）——实现任务的完成定义就是让前一个测试任务转绿

**怎么迁移**：从下一个特性开始，验收标准不允许只写散文——必须落到测试类清单 + 关键守点，人工项单独一节明示。

### 2.5 完成定义证据化 + 反作弊条款

**是什么**："做完"不是一种感觉，是一份证据清单。特性级完成 = 六项证据缺一不可：

```markdown
1. mvn clean verify 全绿（含格式/规约/静态分析/安全扫描全部插件）；
2. 验收 harness 映射表里的每个测试类存在且非空，关键回归测试逐个对得上号；
3. "本特性交付物"逐项存在性核对通过（ls / grep 证据写入报告）；
4. 前序特性测试回归全绿；
5. 全局不变量（H4）逐条自查通过；
6. 产出验收报告：以上证据 + 剩余人工项清单。
```

**反作弊条款**（对"让评估变绿"而不是"让产品变对"的直接防御）：

```markdown
不得通过删断言、@Disabled/pytest.mark.skip、放宽阈值让测试变绿。
实现错了修实现；认为测试本身错了，停下报告。未全绿不得宣称完成。
```

**怎么迁移**：DoD 清单和反作弊条款直接写进工作流（skill 或 PR 模板），验收报告作为特性的固定交付物之一。

### 2.6 输入分层：WHAT/WHY 与 HOW 严格分离

**是什么**：spec 生成（specify）与实施计划生成（plan）的输入严格分层，不混：

| 流程 | 喂什么 | 不喂什么 |
|---|---|---|
| **specify**（定义问题） | 背景价值、用户场景、功能需求、明确不做、验收标准、依赖假设 | 技术选型、类名、模块结构 |
| **plan**（定义解法） | 技术栈、类名签名、模块落位、测试策略 | 需求本身 |

**spec 输入的六段式骨架**（直接可抄）：

```markdown
<特性名>需求：<模块名>——<一句话定位>
背景与价值。<为什么需要，一段话>
用户场景。<2~3 个具体场景，带角色>
功能需求。FR1~FRn，每条可测试
明确不做（边界）。<逐项照搬"先别做"清单>
验收标准。可自动化部分由验收 harness 测试套件承载（全绿即通过），
  关键回归点：<列出守点>；人工项见"做完怎么验"。
依赖与假设。<指向前序交付物；外部依赖>
```

**另外两条纪律**：

- **已有文档资产不重写**——需求文档、技术方案、业界调研直接作为工具输入，工具只负责转成 AI 可消费的格式。但**必须喂最新版**：喂了旧版技术方案，生成的 plan 就按旧结构走偏。
- **文档结构即流程输入**：写文档时按"是什么/想清楚/怎么写/交付物/验收/先别做"组织，下游 specify/plan/tasks 各取所需段落，不需要二次加工。

**怎么迁移**：六段式骨架作为需求文档模板；技术方案文档里显式维护"关键决策 + 为什么"章节（它是宪法和 plan 的共同原料）。

### 2.7 颗粒度匹配的双模式策略

**是什么**：不搞一刀切，按任务颗粒度选协作模式：

| 维度 | 主体开发（greenfield / 大特性） | 增量开发（小改动） |
|---|---|---|
| 工具 | Spec-Kit 完整流程（specify → plan → tasks → implement） | 手动提示词 + AI 编码工具 |
| 颗粒度 | 大（跨模块建架构） | 小（通常 1~3 个文件） |
| 判断标准 | 流程开销 < 工作量 | 流程开销 > 工作量 |
| 宪法/spec 的角色 | 生成依据 | 长期参考（增量仍须遵守宪法、不得破坏 spec 验收标准） |

边界规则要显式写下来：大 feature（新增模块、改宪法、跨多个核心能力）仍走完整流程；小 feature 直接改 + PR。**工具选择跟工作性质匹配**。

**怎么迁移**：在方法论文档里写明两模式的切换条件和例外规则，避免团队在小事上跑重流程（然后因为太重而整个弃用）。

---

### 2.8 方法论固化为 Skill：纪律不依赖自觉

**是什么**：同一个方法论存在三种形态，层层收窄自由度：

```
原理文档（为什么） → 执行指导（怎么做） → Skill / 脚本（照跑）
```

把流程做成 AI 工具的可执行 skill 后，门禁不是"提醒"而是**执行逻辑**：

- 第 0 步做**输入分流**（不同性质的工作走不同模式：代码特性走完整流程、评审/对账类工作走固化检查、演示类工作走调试清单——不硬塞进一个模子）
- 第 1 步强制完整阅读三样材料 + 依赖 grep 核对，不凭记忆
- tasks 生成后设**固定软停点**：任务 ↔ 交付物清单自动比对，差异报告，等人确认再 implement
- **全程不自动 commit / push / 打包**——同步时机由人决定

**Meta 启示**：用 AI 编程工具来管理 AI 编程过程本身。团队 SOP 固化成 skill 后，纪律从"资深工程师的记忆和自觉"变成"流程的默认行为"。

**怎么迁移**：把重复执行 3 次以上的流程写成 skill（或脚本化的命令序列），原理文档保留为 skill 的设计依据。

### 2.9 定向 review 检查单 + "AI 易犯错误清单"飞轮

**是什么**：plan 生成后的人工 review 不泛泛地看，而是**针对本项目已知 AI 失败模式的定向清单**。例如原项目的四条：

> - [ ] 有没有把两个本应分开的模块合并了
> - [ ] 有没有把本应合并的模块拆开了
> - [ ] 有没有把"上下文来源"错放成"可执行工具"
> - [ ] 有没有启用框架的自动执行路径（宪法明令禁用的那条）

背后是一个持续运转的飞轮：

```
发现 AI 跑偏 → 记入"常见陷阱"表（陷阱/症状/修复三列，进项目 AI 指南）
            → 高频的产生两条沉淀：① review 定向检查单条目 ② 回归测试守点
            → 特高频的升格为宪法条款或全局不变量
```

**为什么有效**：AI 的错误不是随机的——同一个项目里它会反复以同样方式跑偏（比如总想启用框架的自动工具执行、总想"改进"已定签名）。错误清单让每次跑偏的代价只付一次。

**怎么迁移**：在项目 AI 指南里开"常见陷阱"表，从第一天开始记；review 检查单从表里生成，不凭空写。

---

### 2.10 质量门禁全链路 + 一个反直觉细节

**是什么**：格式、规约、静态分析、安全扫描**全部挂进构建**（`mvn verify` / `npm run verify` 等价物），pre-commit 本地把关 + CI 双卡：

- 格式化（如 google-java-format / prettier）
- 编码规约（如阿里 P3C）
- 风格兜底（Checkstyle / eslint）
- 缺陷分析（SpotBugs + Find Security Bugs）
- 依赖 CVE 扫描（OWASP Dependency-Check）
- 集成测试默认按 tag 排除、CI 显式控制

**人不做任何格式类 review**——机器能卡的都卡住，人的注意力留给设计。

**反直觉细节**：静态检查是门禁的一部分，**解析失败等于构建失败**，所以编码规范里要包含"工具链兼容性"条款——比如老版本 PMD/ASM 解析不了新语言语法时，宁可规约里禁用该语法形态（原项目明确禁了某些 switch 语法糖），也不给门禁开洞。AI 写代码不会主动考虑你的静态分析工具版本，这条必须写进规范。

**怎么迁移**：门禁清单按语言生态选等价物；"工具链兼容性约束"作为编码规范的一等公民。慢速检查（如 CVE 全量扫描）本地默认跳过、CI 打开。

| 6 | 软门禁"必须停下"清单（§2.2）、DoD 六项证据 + 反作弊条款（§2.5） | 同 2、3 |

### 3.2 必须自己产的（抄不来）

1. **宪法**——从自己项目的关键技术决策提炼，重点写"AI 容易做错"的架构边界；每条带 rationale
2. **全局不变量 5~8 条**——"这还是不是我们那个系统"的最小判据，逐条可 grep 或可测试
3. **AI 易犯错误清单**——跑一阵子才有；一旦开始维护，review 检查单和门禁都从它生长（§2.9 飞轮）
4. **验收 harness 惯例**——"每个坑一条回归测试"的纪律 + 测试类命名/守点格式
5. **唯一权威设计源**——选定一份技术方案文档作为 H1 的仲裁基准，其他文档与它冲突时停下报告

### 3.3 建议落地顺序

```
第 1 步  质量门禁全链路（§2.10）——纯机器，见效最快，先让"硬"的立起来
第 2 步  宪法 + 全局不变量（§2.1、H4）——开工前必须就位
第 3 步  软门禁停下清单 + DoD 证据化（§2.2、§2.5）——写进 AI 指南和 PR 模板
第 4 步  spec 六段式模板 + 验收 harness 惯例（§2.4、§2.6）——从下一个特性开始用
第 5 步  重复流程固化成 skill（§2.8）——等流程手动跑顺 3 次以上再做
第 6 步  错误清单飞轮（§2.9）——持续运转，永不停
```

## 4. 使用边界

这套方法论（尤其 Spec-Kit 完整流程）的适用条件，原项目评估过，值得照抄这个诚实：

**适合**：

- medium-large 规模的 greenfield（从零开发、工程量跨多个模块）
- 需求清晰（上游有需求文档或明确产品决策）
- AI agent 做主体开发
- 团队需要沉淀工程方法论

**不适合**：

- 小 feature、快速原型、单文件改动——流程开销大于收益，切手动提示词模式（§2.7）
- 大型 brownfield 改造——legacy 上下文超出 LLM context limit
- 探索性研究项目——需求未定就跑 spec 会反复返工

**工具层面的注意**：spec 工具链迭代快，实施前锁定一个具体版本，整个开发期间不升级；只用官方核心命令，不引入社区扩展。
