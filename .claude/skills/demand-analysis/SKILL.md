# 需求分析（立项文档链第三篇）

帮用户把定位承诺展开成一份 What 级需求文书：做什么、做到什么程度、不做什么、怎么算做完。它是技术方案与研发实施的直接上游——不是定位宣言的复读，不是技术选型书，那两样分别是链内第二篇和第四篇的事。

用户此刻通常在构思规划期：手里有前两篇（甚至只有一份能力承诺），没有代码、没有实现反馈。默认路径只依赖定位输入与用户拍板；凡是依赖既有资产或参照仓库的步骤，先确认存在才走。

两条铁律贯穿全程：

1. **未拍板不动笔**。框架口径（范围基准、里程碑形态、验收形态、显式偏差）是用户的决策；拍板前只出提纲和输入清单，正文一字不写。
2. **需求是承诺不是愿望清单**。能力清单、指标数值、验收项，每一条都指得上游——定位篇的能力承诺、已拍板的范围决策、或用户显式拍板。**对照参照时，参照有的不等于自己要有的**；拿参照或竞品的能力清单当自己的需求，是本 skill 的事故高发区。

## 第 0 步 · 拍板（口径）

完成判据：四个口径问题用户给出明确答案，缺一个不进第 1 步。

1. **上游输入**：第二篇定位（+ 第一篇调研）在手吗？
   - 在：能力清单、锚点、概念辨析、边界（明说不做什么）就是输入。
   - 只有调研、没有定位篇，但用户有能力承诺：列为输入，显式标注「未经定位篇固化」，第 2 步对账时提示补定位。
   - 两样都没有：退回，本 skill 不凭空立需求——需求是定位承诺的展开。
2. **范围基准**：第一阶段的边界拿什么定？时间盒（N 周）、资源盒、自定范围卡，或参照实现的某个交付窗口/时点。范围基准决定核心功能的收口强度，后续所有「第一阶段不做」都朝它对账。
3. **形态参照**：有先行者的需求文档可对照吗？拿得到原文吗（仓库/公开页）？拿得到则第 1 步加走考古支线；拿不到则降级为公开资料对照，缺的说明即可；没有则直接用 references/doc-structure.md 的通用骨架。
4. **落点与读者**：需求篇落在哪、给谁看（技术方案的直接上游？对外需求书？）。

## 第 1 步 · 输入提炼（有形态参照加考古支线）

**通用部分**——把定位输入提炼成四类清单，交用户过目：

- **能力主线**：定位篇承诺的核心能力，逐条列出——这是核心功能章的骨架。
- **概念模型**：定位篇的概念辨析与定义本体（如「一个 X = 一个 Y」这类），术语表的宪法。
- **边界**：定位明说不做什么、留给后续阶段的路线图——排除项与扩展章的原材料。
- **论据与指标锚点**：定位/调研里与需求相关的硬结论（为什么做、给谁用），正文引用不重证。

**考古支线（仅拿得到参照需求文档原文时走）**：

- 挖立项期首版：`git log --follow` 找参照需求文档的最早提交，`git show <hash>:<path>` 读原文，再读现版，对比结构与形态。
- 三层提取：**骨架层**（章节结构，通常立项期一次定形、全程稳定——可抄）；**粒度层**（What 落到端点/命令/字段/指标级的写法——可抄）；**决策层**（概念模型、范围、验收形态——跟参照的项目走，不照抄）。
- **落差检测（本支线独有的价值）**：拿参照需求文档对照参照的**实际交付**（specs、代码、发布物、课程/里程碑记录），列出滞后点——文档说某能力放扩展、实际核心阶段就交付了，这类「形态 vs 事实」冲突点收进拍板清单，不默认跟文档。参照现版文档混着立项期内容与后续演化，**现版文档既不是立项形态、也不是范围基准**。
- 可学处与反面教材一起总结：文档落后于实现、课后补账是常见病，本项目的流程要显式防它。

完成判据：四类输入清单（+ 考古三层表与落差点清单）交用户过目；与定位矛盾或缺位的事实回报用户，不自行吸收。

## 第 2 步 · 框架拷问

拍板点用选择题（AskUserQuestion）逐个过，未拍板不动笔：

1. **能力清单对账**：需求篇的能力主线与定位篇的核心能力一一对账，多一项少一项都要说明理由。定位清单里没有的，不因为参照有就混进来。
2. **概念模型锁死**：术语表与定位篇概念辨析逐条一致；定义本体进术语表第一行；正文用词与术语表严格一致。
3. **里程碑形态**：日历时间盒 / 交付单元映射表（每单元「能力主线 + 可演示成果」，节奏自定）/ 两者混合。节奏不由项目自控的选映射表，需要硬排期的选时间盒。
4. **验收形态**：产品验收（功能验收 checklist + 指标验收 + 端到端场景验收）是主体；端到端 Demo 要不要定为发布硬条件；项目另有过程层纪律（逐单元验收证据之类）时，拍板过程证据进不进正文——默认不进，元语境留在治理文档（ADR / 流程规定）。
5. **显式偏差逐条拍板**：上游定位与参照形态/事实的冲突处（含第 1 步落差检测产出的每一条），逐条选择题。默认**上游赢、理由写进文档**——需求篇对参照形态的每处显式偏差都留得下理由，才经得起逐篇对照。

完成判据：全部拍板点有明确答案。

## 第 3 步 · 成文

按 [doc-structure.md](references/doc-structure.md) 的骨架成文。三条写作纪律：

- **What 不 How**：粒度下限是端点、命令、数据字段、指标数值——下游技术方案能直接引用；粒度上限是「做什么」，选型论证、模块划分、接口设计出现即挪进未决事项表（注明决议时间），不留在正文。
- **排除与纳入同样明确**：每个核心功能小节带「第一阶段不做」清单；范围基准之外的能力与机制进扩展章或社区共建章——不消失（消失会让后续阶段无处可接），也不混入核心。
- **产品口径**：过程型、学习型元语境（跟拍、复盘、工具链）不进正文；范围基准引用的参照公开事实（交付窗口、发布物）可以进，但以事实形态引，不以学习作业形态写。

## 第 4 步 · 对账自检

写完逐项过，任何一项不过就改文，不带病交付：

- **上游一致**：能力清单与定位篇对得上账；正文不新增定位/调研没有的事实性断言；用词与术语表严格一致。
- **What/How 分界**：全文无选型论证（有则在未决表）；每个核心功能小节有「第一阶段不做」。
- **粒度下限**：端点清单、命令清单、数据表字段、非功能指标数值到位。
- **可验收性**：验收章的 checklist 与核心功能小节一一对应；端到端场景验收覆盖全部核心能力与触发源；指标验收与第 8 章数值一致。
- **偏差复核**：拍板过的每处显式偏差都在正文留了理由；落差检测产出的滞后点没有一条被无意识地照抄或无视。

完成判据：五项全过。

## 第 5 步 · 沉淀

- 需求阶段新立的概念（术语表新增行）：仓库有词汇表惯例就按惯例沉淀，没有就跳过。
- 口径决策若同时满足三条——难逆、无上下文会困惑、真实取舍——记一条 ADR；显式偏差（上游与参照形态冲突的拍板）通常够第三条。
- 成文或对账中发现与定位篇/调研结论冲突：停下来报告用户，既不擅自改上游也不硬写。
