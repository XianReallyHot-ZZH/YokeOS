# YokeOS：企业 Agent 底座（Agent Harness OS）

## 定位

装在企业自己基础设施上的 Java 原生 Agent 底座（Agent Harness OS）：私有部署、全链路可审计、不锁任何云。

## 愿景

成为严监管企业信赖的 Agent 运行底座。让银行、政府、电信、能源、医疗这些数据不出域、行为必须可审计、新组件必须过现有安全合规流程的企业，把每一个业务 Agent 都跑在自己能完全掌控的基础设施上——像操作系统管理一群进程一样，管理一群 Agent。

YokeOS 是用 Java 构建的开源 Agent 底座。一个目录定义一个 Agent，一个底座运行一群 Agent，私有部署，数据不出域。原生对接 MCP 与 A2A 开放协议，覆盖模型接入、推理循环、记忆、工具调用、通知定时、对外服务等核心能力，全链路审计从第一天落库。让一群 Agent 像一群进程跑在操作系统上一样，可靠地运行和被治理。

Java 企业体系不应该在「运行和管理一群 Agent 的底座」这一层留空。这一层今天仍然稀薄：框架层（Spring AI、LangChain4j、AgentScope Java）已经成熟，但装在自己 K8s 上、跟 Spring 运维链咬合、不锁云的完整底座，离被企业生产验证的规模化形态还很远。补上它，跟 Spring AI 当年补上「Java 的 LLM 调用层」是同一个逻辑：不是因为 Java 比别的语言强，而是一个完整的生态不应该在关键层级留空。

YokeOS 用「Agent OS / Harness OS」这个框架理解和构建自己，但不把自己锚在概念上，锚在它背后不会变的企业刚需上：私有部署、完全可审计、跟 Java 体系对齐、数据不出企业、IT 能掌控。「Agent OS」这个词正在被平台巨头收编为营销类目，它可能被稀释、被改名、被上下层吸收；但只要企业还要求 Agent 的行为可审计、数据不出域、系统能纳入现有治理，这个需求就在。锚在概念上的项目随概念漂移，锚在需求上的项目不随。

## 为什么需要 YokeOS

每家企业都有该交给 Agent 的活，需求侧已无悬念。但真正卡住企业的不是「做出一个 Agent」，是「让它在企业里可控地跑起来」：核心数据不出企业，把业务 Agent 放在 SaaS 或公有云控制平面上过不了合规；执行是黑盒，没人敢在一个不留痕的系统上签字放行——行业调研里 88.4% 的组织过去一年经历过 AI Agent 相关安全事件，31% 对 Agent 系统缺乏可观测性或可审计性；权限超配与技能供应链正在成为新的攻击面。这些问题没有一个是「模型不够强」能解决的，全都是运行底座的问题。

对后端事实标准是 Java 的企业，这个底座还有一道接缝成本：选跨语言栈的项目，就要在两套技术栈的接缝处写胶水——对接自己的 Java 服务、复用自己的 Java 运维链、走自己的 Java 审计流程；等平台巨头，拿到的是绑定各自云的组件与控制平面。Java 体系在这一层已有先行者（OryxOS 已经在这个位置起步），但「装好就跑、跟 Spring 运维链咬合、不锁云的完整底座」仍属稀薄。这个位置值得被补上，也容得下补的人。

更深一层的判断是：**让 Agent 在生产环境可靠工作，瓶颈通常不在模型本身，而在 Agent 的运行环境。** 这个判断是这个品类被反复验证的共识——消费级 Agent 的结构性安全代价、工程级 Agent 的治理空白、先行者的立项判断，都指向它。YokeOS 不宣称首创这个判断，选择站在它上面：做的不是又一个 Agent，而是这个让一群 Agent 可靠运行和被治理的底座本身。

## Agent runtime、Harness 与 Agent 底座

agent runtime 是让单个 Agent 跑起来的执行内核，负责调用模型、执行工具、管理上下文、控制推理循环。Harness 是套在模型外面、让「会生成文本的模型」变成「能可靠做事的 Agent」的运行骨架：驱动 reason → act → observe 的循环、组装上下文、约束工具边界、记录审计——裸模型只会生成文本，harness 才让它可靠、安全地做事。Agent 底座（Agent Harness OS）在 runtime 与 harness 之上，管理的是一群 Agent：多个 Agent 的生命周期、统一的对外渠道与对内接入、统一的记忆与知识、多租户与治理，以及分布式形态下的跨节点协作。

借操作系统的类比说：runtime 像单个进程的执行环境，Agent 底座像管理一群进程、调度资源、提供共享服务和治理的那一层。一句话，**runtime 和 harness 让一个 Agent 跑起来、跑得对，Agent 底座让一群 Agent 在企业里被管起来。** YokeOS 是后者。

## 核心能力

### 对接 LLM

通过 Provider 抽象统一对接主流大模型，Agent 不感知具体厂商，运行时切换无锁定，支持本地推理。多 Provider 并存通过显式映射区分。

### ReAct 循环

Agent 的推理引擎，自己实现不套外部框架。LLM 思考是否调工具、调哪个，底座执行后回填结果，LLM 再决定下一步，直到给出最终响应或达到最大迭代次数。循环行为完全可控。

### 记忆

让 Agent 跨对话保留状态。会话记忆加长期记忆两层，长期记忆用文件形态、关键词检索，接口预留向量检索升级空间。

### 工具体系

Agent 通过工具操作外部世界。内置文件、Shell、HTTP 等基础工具；工具调用经路径、命令、域名三重白名单校验，在沙箱边界内执行，全程留痕。扩展三档接入，门槛从低到高：零代码写 Agent 目录加复用现成 MCP server、轻代码自写 MCP server、重代码用原生方法。

### 通知与定时

Agent 干完活要能触达人，没人触发也要能自己跑。Notify 把执行结果推到配置的通知渠道；定时任务让每个 Agent 按 cron 到点自动运行，执行历史可查。

### 对外服务

所有能力通过 REST API 对外暴露，业务系统 HTTP 接入，任何语言可集成。Web 管理台覆盖 Agent、Provider、沙箱白名单与会话的日常管理。

## 核心特性

- 🤖 **一个目录 = 一个 Agent**：一个包含 `AGENT.md` 的目录定义一个 Agent，不用写代码，多个 Agent 同实例并存
- 📡 **动态管理**：REST 增删改查，一句话生成 Agent 草稿，目录就位即上线，免重启
- 🛠️ **Skill 能力模板**：SKILL.md 封装可复用的程序性知识，Agent 按需引用；兼容 agentskills.io 开放格式，社区技能经企业审查后可导入
- ⏰ **到点自跑**：按 Agent 的 cron 定时任务加通知渠道，执行全程留痕
- ☕ **Java 原生**：基于 Java 21 与 Spring Boot，单可执行 JAR 部署，复用企业现有 Java 运维工具链
- 🔒 **私有可控**：装在企业自己的 K8s、虚拟机或物理机上，数据不出域，不锁任何云
- 🛡️ **安全隔离**：文件、命令、域名三重白名单沙箱，最小权限，凭证走企业密钥体系不落地，全链路审计从第一天落库
- 🧠 **自实现 ReAct**：核心推理循环自己实现，不套外部 Agent 框架，机制完全可控
- 🔌 **对接开放标准**：工具用 MCP，Agent 协作用 A2A，技能用开放格式，与生态协同不另立协议
- 🌐 **无状态可扩展**：运行实例无状态、状态外置，从架构起为走向分布式留好路

## 路线图

我们的开发理念是：慢就是快，克制且聚焦。先把单机的运行时内核做扎实，让一个节点上运行和管理一群 Agent 这件事真正可用，再在它之上逐步生长出分布式能力。第一阶段不追求产品功能差异化：以被验证过的参照实现为基准逐节交付、等价验收，把工程过程本身做扎实，产品层面的分叉留给有真实使用判断之后。

- **阶段一（当前）单机运行时内核**
  - 与参照实现对齐的完整运行时内核：对接 LLM、自实现 ReAct、两层记忆、工具与沙箱、通知与定时、REST API 与 Web 管理台
  - 一个目录 = 一个 Agent、动态管理、多 Agent 并存、打包发布
  - 审计落库与白名单沙箱从第一天就在
- **阶段二（规划）能力补齐与底座分布式**
  - 知识库与语义记忆：文档导入、切分、向量化检索，补齐能力版图
  - 节点无状态化、状态外置、多副本部署，支撑更大规模与高可用
  - 平台基线升级（Spring Boot 4 + Spring AI 2.0）
- **阶段三（愿景）跨节点 Agent 协作**
  - 引入 Agent 通信底座，对接 A2A
  - 让多节点上的 Agent 跨节点发现、委托、可靠异步协同
- **横向能力（伴随各阶段逐步补齐）**
  - 多租户、SSO、分级审批（HITL）、完整审计与工具策略、可观测、Web 管理

## 设计原则

- **底座优先于 Agent**：最重要的交付不是某个强大的 Agent，而是让任意 Agent 都能可靠运行的环境
- **自实现核心，可控优先**：核心推理循环自己实现，底层模型协议适配复用成熟库，不重复造轮子
- **配置即 Agent**：一个 Agent 由一个目录定义（`AGENT.md` 加可选附属资源），而不是由代码写出
- **对接开放标准**：工具用 MCP、协作用 A2A、技能用开放格式，与生态协同
- **无状态实例，状态外置**：从单机平滑走向分布式的前提
- **安全是地基不是补丁**：工具来源受控、最小权限、强制沙箱、凭证不落地、全链路可审计，安全从第一天就在架构里
- **分阶段克制**：当前只做运行时内核的最小完备集，治理与重型分布式基础设施留到后续，每次架构升级都用真实使用数据证明其必要性
- **复刻型起步**：以被验证过的参照实现为基准逐节复刻运行时内核，第一阶段不做产品功能差异化，差异化立在过程——可追溯的规格、验收证据与方法论沉淀
- **锚需求不锚概念**：锚私有、可控、可审计、与 Java 体系对齐这些不会变的企业刚需，不锚可能被稀释或改名的品类名词
