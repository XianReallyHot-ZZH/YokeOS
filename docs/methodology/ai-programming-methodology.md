## 0. 这套方法论解决什么问题

把执行交给 AI 之后，真正的风险不是"写错"——写错测试能抓。真正的风险是：

> **每一步局部合理、整体漂移**——最后交付出来的不是设计中的那个系统。

漂移有四种典型形态，这个分类本身是整套方法论的地基：

| 漂移形态 | 表现 | 为什么危险 |
|---|---|---|
| **发明** | 造出文档里不存在的公共类、配置项、端点 | 单看都"挺合理"，累积起来系统长歪 |
| **顺手优化** | 把已定签名"改进"一下、配置键换个"更好"的名字 | 下一步按文档喂料时全部对不上 |
| **提前实现** | 把"先别做"清单里的东西顺手做了 | 复杂度背上身，还没有信号支撑 |
| **臆造 API** | 写出根本不存在的第三方方法 | 编译期炸算好的，更糟的是碰巧存在但语义不同 |

防漂移要两侧同时做：**目标侧**在开工前把决策冻结下来（§2 立项文档链），**执行侧**在过程中对齐冻结的决策（§3 门禁体系）。

执行侧的防御是**分层**的——每层拦的漂移入口不同，缺一层就有一类漂移没人管：

| 防御层 | 手段 | 见 |
|---|---|---|
| 设计层 | 宪法原则 + 四条设计母题 | §3.1、§3.2 |
| 流程层 | 硬/软门禁 + H0–H6 关卡 | §3.3、§3.4 |
| 静态层 | 全局不变量 + 质量门禁全链路 | §3.4（H4）、§3.9 |
| 单测层 | 验收 harness（每个坑一条回归测试） | §3.6 |
| 运行时层 | 对账法（真实调用逐表核对 + 集成测试固化） | §3.8 |

长跑问题（中断再入场、上下文衰减、成本节奏）不属于某一层，单独一节（§3.13）。所有后续机制都围绕"两侧 × 五层"展开。

## 1. 总纲

一句话：

> **文档链给决策，SDD 给目标，Harness 给边界，Loop 给可控执行。**

| 层 | 载体 | 回答的问题 |
|---|---|---|
| **立项文档链** | 调研 → 定位 → 预求 → 方案 → 实施指南 | 为什么做、是什么、做什么、怎么做、用什么方式做（决策冻结，见 §2） |
| **SDD**（Spec-Driven Development） | constitution → specify → clarify → plan → tasks → analyze → implement | 要做什么、不做什么、按什么顺序 |
| **Harness** | 测试套件 + 静态检查 + 门禁条款 | 做出来的对不对、过程越没越界 |
| **Loop** | 可执行的工作流（skill / 脚本 / 命令序列） | 每一步可控、可停、可回退 |

两点说明：

- 表中的流程阶段名（constitution / specify / clarify / plan / tasks / analyze / implement）以 Spec-Kit 为**实例**，不是机制本身——换成任何规格工具或手工文档序列，各阶段职责不变，方法论照用。
- "可停、可回退"不是品行要求，是有过代价的：**授权颗粒度 = 回滚颗粒度**（§3.3 的任务书教训）。所以停点要小、同步（commit / push）时机永远由人掌（§3.11）。

权力分配原则：

> **AI 可以执行一切，但改变设计的权力永远不下放。**

落到操作上是一句分野，也是整套门禁的划分标准：

> **能机器判的绝不留给人，机器判不了的绝不自行发挥。**

## 2. 立项文档链：把决策冻结在执行之前

**是什么**：写第一行代码之前，用一组文档把立项时最容易被反复推翻的五类决策，每类一份、一次性冻结：

| 文档 | 冻结的决策 | 不冻结会发生什么 |
|---|---|---|
| 业界调研 | **为什么值得做**：空白在哪、别人做到哪 | 做到一半怀疑"是不是重复造轮子"；没看清相邻项目已经把路走了 |
| 项目定位 | **是什么、不是什么**：与相邻项目的边界 | 项目被拉扯成什么都做；贡献者不知道该提什么 PR |
| 需求文档 | **做什么**：功能边界 + 验收标准 | 范围膨胀，"扩展功能"悄悄变成"核心功能" |
| 技术方案 | **怎么做**：技术栈、模块边界、关键取舍 | 每实现一个模块重新吵一次架构；AI 实现时没有仲裁基准 |
| 实施指南 | **用什么方式做**：人机分工、流程选型 | 每个人用自己的方式驱动 AI，产出不可比、不可沉淀 |

一个易混点：文档链里的**需求文档是项目级**——冻结整个项目的功能边界与验收（实物见 §6 DemandAnalysis.md）；它与**特性级 spec 输入**（六段式骨架，§3.5）是两层产物，后者逐特性生成、喂给 specify。不要给项目级需求套特性级的模板。

**为什么有效**：立项文档链的本质不是"把想法想清楚"，而是**让决策停止流动**——后续所有执行（无论人还是 AI）都在冻结的决策上跑。它与门禁体系互补成完整闭环：**文档链是目标侧防漂移（冻结决策），门禁是执行侧防漂移（对齐决策）**。没有文档链，门禁没有仲裁基准；没有门禁，文档链就是一堆死文档。

**AI 时代的变化**：文档的回报率变了。这组文档不再只是写给人的交付物，而是开发流程的直接输入——需求文档喂 specify、技术方案喂 plan、验收章节直接变成 acceptance criteria、关键技术决策提炼成宪法。写文档由此成为杠杆最高的编程活动：**文档质量直接决定 AI 产出的代码质量**。

**四条纪律**：

1. **每份文档动笔前先回答"谁消费它"**。没有消费者的文档必然腐烂。消费者分三类：外部（社区、贡献者、决策者）、流程（specify / plan / 门禁仲裁）、用户（使用手册）。原项目立项五份文档恰好各归其位：定位与调研面向外部，需求与方案面向流程，实施指南面向流程与团队。
2. **文档预算与项目野心成正比**。完整五份链条适合 greenfield 中大型 + 社区开源项目；**最小可行版本三份：定位（含调研结论）、需求、方案**。给小工具项目配五份文档是自我感动。
3. **探索期故意不冻结**。需求未定时提前冻结会放大错误——冻结是放大器：想对了放大对的，想错了放大错的。探索性项目先跑通，再回头补文档链。
4. **喂给下游的必须是最新版**（同 §3.5 的纪律）：文档与实现脱节时，下游按旧文档生成的规格会整体走偏。

**怎么迁移**：按决策冻结表逐行问自己"这个决策冻结了吗、冻结在哪份文档里"；三份起步，其余按项目规模递增。

## 3. 十三项可迁移资产

### 3.1 宪法机制：把"不可协商"变成有治理的文档

**是什么**：项目开工前，从技术方案的关键决策中提炼一份 constitution（非协商原则集），凌驾于一切个人偏好与临时便利。

**为什么有效**：AI（和新成员）对"为什么这么定"没有上下文，只给规则会形式化遵守甚至"合理化绕过"；带上 rationale 的原则才能在边界情形下做出正确判断。

**关键做法**：

- 每条原则 = 规则 + **Rationale**（违反了会发生什么具体坏事，如"启用自动工具执行会导致工具被调两次"）
- **显式标注"最容易被写错的一条"**——不平均用力，把已知高频违规点标红
- **语义化版本 + 修订治理**：MAJOR（原则删除/重定义）/ MINOR（新增原则）/ PATCH（澄清措辞）；修订必须走 PR、说明动机与影响、**同步更新所有受影响的模板和指南**；文件头维护 Sync Impact Report
- **AI 不得自改宪法**——修改宪法属于设计变更，永远走软门禁（停下报告）
- 宪法与项目级 AI 指南（CLAUDE.md / AGENTS.md）保持**双向一致**：指南以宪法为准，两者不得矛盾

**怎么迁移**：任何项目 AI 开发开工前先写。提炼来源不是编码规范（那些交给工具，见 §3.9），而是**架构边界决策**——重点是那些"AI 很容易顺手做错"的地方。8 条左右为宜，超过 15 条说明还没想清哪些真正不可协商。

### 3.2 设计母题：设计层的防漂移纪律

**是什么**：门禁拦的是执行越界，拦不了设计本身走样。从技术方案的关键取舍中，提炼几条**写代码之前**就能套用的设计母题（示范工程第一阶段总结出的四条）：

1. **接口先行，按档实现**：先定接口再写实现；接口要用"最重的未来实现"来检验——拿脑子里最重的那个未来用法套一遍接口，套不进去就改接口，而不是迁就眼前的实现去改接口。
2. **信号驱动升级**：不为想象中的需求预先加复杂度。扩展点按"方向 / 挂载位置 / 触发信号"三列预写在方案里——信号出现才动手，不凭预感。
3. **分阶段克制**：每个阶段只解决本阶段的问题；下一阶段的问题留给下一阶段，复杂度不预支。
4. **同一入口复用，不另开路径**："凡是出现第二条路径，迟早行为不一致。"要新能力先问能否挂在既有入口上，不能因为"这次不太一样"就新开一条。

**为什么有效**：四条各对一种设计漂移——接口先行防"实现倒逼设计"，信号驱动防"提前实现"在设计层的变种，分阶段克制防范围蔓延，同一入口防路径分裂。它们与 H0–H6 互补：门禁管执行时越界，母题管规划时走样。

**怎么迁移**：写进技术方案"关键决策 + 为什么"章节的旁边，作为设计评审检查项；每条配一个本项目的正反实例。

### 3.3 硬/软双轨门禁 + "必须停下"清单

**是什么**：按"谁来判"把门禁分成两轨：

| | 硬门禁 | 软门禁 |
|---|---|---|
| 谁来判 | 机器（测试、构建、静态检查、脚本核对） | 人（AI 停下报告，等确认放行） |
| 不过会怎样 | 构建失败 / 任务不得推进 | 流程暂停，等人拍板 |
| 管什么 | 结果可自动验证的事 | 需要判断的事（设计变更、文档冲突、范围调整） |
| 防的失败模式 | 做错了没发现 | **自作主张** |

**核心是软门禁的触发清单**——把"AI 什么时候必须停下来问"从模糊的品行要求变成可枚举、可执行的条件：

```markdown
遇到下列任一情况，立即停下、向用户报告、等确认后继续，不得自行决定：
1. 需要创建交付物清单之外的任何对外概念（public 类型、配置键、数据表、API 路径、Profile 字段）；
2. 需要修改任何已定字面量（类名、方法签名、配置键、表列名、端点路径）；
3. 两份权威文档之间冲突（不自行仲裁）；
4. 需要修改前序交付的公共接口（当前特性文档明确列为"改造点"的除外）；
5. 第三方 API 在本地依赖中核实不到（写前核实，核实不了不写）；
6. 需要新增 plan 未列明的第三方依赖。
```

**为什么停点要小——一个真实的教训**。示范工程的工作方式演化到第二代时，做法是"把 45 条交互提示词归纳成结构化任务书，一次性授权执行"。结果 AI 越权干活，只能整体回滚（源材料原话："你错了，我不是让你干活……先回滚改动"）。教训值得单独记住：

> **授权颗粒度 = 回滚颗粒度。**

大颗粒一次性授权省下的确认次数，会在回滚时连本带利还回去。这就是软门禁停点、以及"全程不自动 commit / push"（§3.11）存在的理由——每一步可停，损失才可控。

**怎么迁移**：清单直接抄走，按项目调整条目。判定标准就一条——这件事机器能不能判？能，做成硬门禁；不能，进停下清单。

### 3.4 H0–H6 门禁骨架（最值得整体抄走的表）

**是什么**：把门禁按"挂在流程哪个位置"组织成七道关卡：

| 门禁 | 管什么 | 核心条款 | 防什么 |
|---|---|---|---|
| **H0 开工纪律** | 前置阅读 + **依赖存在性检查** | 动手前必读：当次特性文档全文、技术方案对应章节、前序各次交付物清单；对前序交付物逐个 grep 确认存在，缺了停下补前序，不许跳步自造 | 上下文断裂 |
| **H1 设计保真** | 唯一权威设计源 | 每个公共概念必须能在权威文档找到出处；公共概念白名单制——交付物清单之外的对外概念一律停下报告；已定字面量逐字保真，禁止顺手改进；文档与代码冲突时**文档优先**——要改行为先改文档、再按文档改代码；**"不做清单"与"要做清单"同等硬度**（不写其功能、不留 TODO 桩、不预埋参数） | 发明 / 顺手优化 / 提前实现 |
| **H2 跨阶段契约** | 前序交付的公共接口 | 只可使用不可修改（文档明确列为"改造点"的除外）；本次结束时**前序所有测试必须仍全绿**；需要前序未交付的能力时停下报告，不就地自造替代品 | 破坏契约 |
| **H3 API 真实性** | 第三方 API | 编写前先在本地依赖里核实存在（`dependency:tree`、翻 jar 源码）；不新增 plan 未列明的依赖 | 臆造 API |
| **H4 全局不变量** | 整体性判据 | 从宪法和反复钉的设计中提炼 N 条"无论做哪个特性永远成立"的不变量，**每次交付前逐条自查** | 整体漂移 |
| **H5 实现质量** | 代码内纪律 | 异常不吞（每个 catch 要么落审计/日志要么上抛）；不过度设计（单实现不建接口）；注释只写"为什么"；命名与文档词汇一致 | 过度工程 |
| **H6 完成定义** | 收口 | 证据化 DoD + 反作弊条款（见 §3.7） | 虚假完成 |

**H4 全局不变量**值得单独说：它是"这还是不是我们那个系统"的**最小判据**——比如"每次外部调用成败都落审计表"、"凭证只走环境变量，grep 无明文 key"、"全程同步阻塞，出现异步框架即违规"。条数少（5~8 条）、逐条可 grep 或可测试、每次交付前过一遍。这是对"局部合理整体漂移"最直接的一味药。

**怎么迁移**：整表抄走，H4 的不变量必须自己提炼（见 §4）。

### 3.5 输入分层：WHAT/WHY 与 HOW 严格分离

**是什么**：spec 生成（specify）与实施计划生成（plan）的输入严格分层，不混：

| 流程 | 喂什么 | 不喂什么 |
|---|---|---|
| **specify**（定义问题） | 背景价值、用户场景、功能需求、明确不做、验收标准、依赖假设 | 技术选型、类名、模块结构 |
| **plan**（定义解法） | 技术栈、类名签名、模块落位、测试策略 | 需求本身 |

**spec 输入的六段式骨架**（直接可抄，注意这是**特性级**模板）：

```markdown
<特性名>需求：<模块名>——<一句话定位>
背景与价值。<为什么需要，一段话>
用户场景。<2~3 个具体场景，带角色>
功能需求。FR1~FRn，每条可测试
明确不做（边界）。<逐项照搬"先别做"清单>
验收标准。可自动化部分由验收 harness 测试套件承载（全绿即通过），
  关键回归点：<列出守点>；人工项见"做完怎么验"。
依赖与假设。<指向前序交付物；外部依赖>
```

**六条纪律 + 一个附注**：

1. **两级模板不混用**：项目级需求文档（§2）冻结整个项目做什么；六段式是特性级 spec 输入。给项目级需求套六段式，会把项目文档写成一份放大的特性规格。
2. **已有文档资产不重写**——需求文档、技术方案、业界调研直接作为工具输入，工具只负责转成 AI 可消费的格式。但**必须喂最新版**：喂了旧版技术方案，生成的 plan 就按旧结构走偏。
3. **文档结构即流程输入**：写文档时按"是什么/想清楚/怎么写/交付物/验收/先别做"组织，下游 specify/plan/tasks 各取所需段落，不需要二次加工。
4. **需求排序只用依赖顺序，不用 P1/P2/P3**——优先级标记会被误读成"靠后的可以不做"。
5. **评审类工作是两段式输入**：深度技术评审先产出文档（业界方案对比 + 本项目设计结论），该文档再作为下一特性 specify 的素材——"评审产文档、文档产 spec"，不直接从评审结论跳到代码。
6. **早期试错产物不清理**：specify 每次新开编号目录、互不覆盖，试错史保留无害。

附注（工具链）：规格工具一般自带 analyze（spec/plan/tasks 间一致性检查）与 converge（评估代码库相对规格的缺口、把未建工作追加为任务）——后者是"实现已经漂移后重新对账"的出口。

**怎么迁移**：六段式骨架作为特性级 spec 输入模板；项目级需求文档按 §2 决策冻结表组织（实物见 §6）；技术方案文档里显式维护"关键决策 + 为什么"章节（它是宪法和 plan 的共同原料）。

### 3.6 验收即代码（Acceptance Harness）

**是什么**：每个特性的验收标准分两层——

- **自动化层 = 具体到测试类名和守点的测试套件**，写进特性文档，`mvn test`（或等价命令）全绿即"机器判卷"通过
- **人工层 = "做完怎么验"清单**，只放机器判不了的项目（如真实冒烟、依赖确认）

**核心纪律**：

> **"想清楚"阶段点过名的每个坑，都有一个回归测试把它永久钉死。**

坑不再依赖人的记忆，变成二进制的存在性。配套的三个习惯：

- spec 里每个 User Story 带 **Independent Test**——不依赖其他故事就能独立验证的测试设计（"注入一个注册失败，核对已写的目录被回滚"）
- tasks 里测试任务可并行标记 `[P]`，且**测试先于实现**（"T005 写测试 → T006 实现，让 T005 转绿"）——实现任务的完成定义就是让前一个测试任务转绿
- **测试名与文档词汇对账**：文档里的中文方法名译成语义等价的英文名落地，用 `@DisplayName` 保留原文——"关键回归测试逐个对得上号"由此变成机器可查，不靠人认

**怎么迁移**：从下一个特性开始，验收标准不允许只写散文——必须落到测试类清单 + 关键守点，人工项单独一节明示。

### 3.7 完成定义证据化 + 反作弊条款

**是什么**："做完"不是一种感觉，是一份证据清单。特性级完成 = 六项证据缺一不可：

```markdown
1. mvn clean verify 全绿（含格式/规约/静态分析/安全扫描全部插件）；
2. 验收 harness 映射表里的每个测试类存在且非空，关键回归测试逐个对得上号；
3. "本特性交付物"逐项存在性核对通过（ls / grep 证据写入报告）；
4. 前序特性测试回归全绿；
5. 全局不变量（H4）逐条自查通过；
6. 产出验收报告：以下证据 + 剩余人工项清单。
```

**验收报告的固定结构**（给 reviewer 的导读，三段式）：

```markdown
1. 改动点：按模块分组，每处一句动机；前序交付物被触碰的单独标出；
2. 重点 review 清单：3~6 条，按风险排序，给到行级定位；
3. 验证命令块：可直接复制执行 + 每条命令的预期结果。
```

证据是给门禁的，导读是给人的——单人流里，这个"人"是两周后的你自己。

**反作弊条款**（对"让评估变绿"而不是"让产品变对"的直接防御）：

```markdown
不得通过删断言、@Disabled/pytest.mark.skip、放宽阈值让测试变绿。
实现错了修实现；认为测试本身错了，停下报告。未全绿不得宣称完成。
```

**怎么迁移**：DoD 清单和反作弊条款直接写进工作流（skill 或 PR 模板），验收报告（证据 + 导读）作为特性的固定交付物之一。

### 3.8 对账法：运行时层的整体判据

**是什么**：单测证明"零件对"，不证明"整机没长歪"。在每个集成阶段（或每次大交付），拿一次**真实调用**逐表核对系统留下的痕迹：

- **该留的留下了**：每个环节按设计应写入的表 / 日志 / 状态，逐表核对确实写了、字段齐；
- **不该留的没多出来**：没有任何表多出设计之外的痕迹——多了，说明有代码在文档之外行动；
- **同源一致**：同一事实在多个入口 / 多个视图里的记录一致（多入口多面同源）。

然后把对账清单**固化成端到端集成测试**（如 `@Tag("integration")` 的 FlowIT，按入口一套），让"整机符合设计"从此每次构建可判。

**为什么有效**：这是对"局部合理、整体漂移"在**运行时**的直接检测——H4 不变量是静态 grep，验收 harness 是单功能单测，对账法是全链路真实调用。三层各管一段，缺一层就有一类漂移拖到收尾才发现。

**怎么迁移**：进入"全流程串联"阶段（特性之间开始集成）时启用；对账清单从技术方案的"每次外部调用应留下哪些痕迹"一节生成；先手工对账一次，清单稳定后立刻固化成集成测试。

### 3.9 质量门禁全链路 + 一个反直觉细节

**是什么**：格式、规约、静态分析、安全扫描**全部挂进构建**（`mvn verify` / `npm run verify` 等价物），pre-commit 本地把关 + CI 双卡：

- 格式化（如 google-java-format / prettier）
- 编码规约（如阿里 P3C）
- 风格兜底（Checkstyle / eslint）
- 缺陷分析（SpotBugs + Find Security Bugs）
- 依赖 CVE 扫描（OWASP Dependency-Check）
- 集成测试默认按 tag 排除、CI 显式控制

**人不做任何格式类 review**——机器能卡的都卡住，人的注意力留给设计。

**反直觉细节**：静态检查是门禁的一部分，**解析失败等于构建失败**，所以编码规范里要包含"工具链兼容性"条款——比如老版本 PMD/ASM 解析不了新语言语法时，宁可规约里禁用该语法形态（示范工程明确禁了某些 switch 语法糖），也不给门禁开洞。AI 写代码不会主动考虑你的静态分析工具版本，这条必须写进规范。

**怎么迁移**：门禁清单按语言生态选等价物；"工具链兼容性约束"作为编码规范的一等公民。慢速检查（如 CVE 全量扫描）本地默认跳过、CI 打开。

### 3.10 颗粒度匹配的双模式策略

**是什么**：不搞一刀切，按任务颗粒度选协作模式：

| 维度 | 主体开发（greenfield / 大特性） | 增量开发（小改动） |
|---|---|---|
| 工具 | Spec-Kit 完整流程（specify → plan → tasks → implement） | 手动提示词 + AI 编码工具 |
| 颗粒度 | 大（跨模块建架构） | 小（通常 1~3 个文件） |
| 判断标准 | 流程开销 < 工作量 | 流程开销 > 工作量 |
| 宪法/spec 的角色 | 生成依据 | 长期参考（增量仍须遵守宪法、不得破坏 spec 验收标准） |

边界规则要显式写下来：大 feature（新增模块、改宪法、跨多个核心能力）仍走完整流程；小 feature 直接改 + PR。**工具选择跟工作性质匹配**。

**怎么迁移**：在方法论文档里写明两模式的切换条件和例外规则，避免团队在小事上跑重流程（然后因为太重而整个弃用）。

### 3.11 方法论固化为 Skill：纪律不依赖自觉

**是什么**：同一个方法论存在三种形态，层层收窄自由度：

```
原理文档（为什么） → 执行指导（怎么做） → Skill / 脚本（照跑）
```

把流程做成 AI 工具的可执行 skill 后，门禁不是"提醒"而是**执行逻辑**：

- 第 0 步做**输入分流**（不同性质的工作走不同模式：代码特性走完整流程、评审/对账类工作走固化检查、演示类工作走调试清单——不硬塞进一个模子）
- 第 1 步强制完整阅读三样材料 + 依赖 grep 核对，不凭记忆
- tasks 生成后设**固定软停点**：任务 ↔ 交付物清单自动比对，差异报告，等人确认再 implement
- **全程不自动 commit / push / 打包**——同步时机由人决定（授权颗粒度 = 回滚颗粒度，§3.3）

**固化的对象不止开发流程一种**：工程地基初始化（质量门禁全链路 + 日志/监控/OpenAPI/统一响应体一次装好）、前端生成（设计 token 与"只读 / 只调既有接口"的边界约束）同样可以固化成 skill——示范工程三者都有。判断标准不变：重复执行 3 次以上的流程就值得固化。

**Meta 启示**：用 AI 编程工具来管理 AI 编程过程本身。团队 SOP 固化成 skill 后，纪律从"资深工程师的记忆和自觉"变成"流程的默认行为"。

**怎么迁移**：把重复执行 3 次以上的流程写成 skill（或脚本化的命令序列），原理文档保留为 skill 的设计依据。

### 3.12 定向 review 检查单 + "AI 易犯错误清单"飞轮

**是什么**：plan 生成后的人工 review 不泛泛地看，而是**针对本项目已知 AI 失败模式的定向清单**。例如示范工程的四条：

> - [ ] 有没有把两个本应分开的模块合并了
> - [ ] 有没有把本应合并的模块拆开了
> - [ ] 有没有把"上下文来源"错放成"可执行工具"
> - [ ] 有没有启用框架的自动执行路径（宪法明令禁用的那条）

背后是一个持续运转的飞轮：

```
发现 AI 跑偏 → 记入"常见陷阱"表（陷阱/症状/修复三列，进项目 AI 指南）
            → 高频的产生两条沉淀：① review 定向检查单条目 ② 回归测试守点
            → 特高频的升格为宪法条款或全局不变量
```

**为什么有效**：AI 的错误不是随机的——同一个项目里它会反复以同样方式跑偏（比如总想启用框架的自动工具执行、总想"改进"已定签名）。错误清单让每次跑偏的代价只付一次。

**怎么迁移**：在项目 AI 指南里开"常见陷阱"表，从第一天开始记；review 检查单从表里生成，不凭空写。

### 3.13 长跑：中断再入场、上下文回充与成本节奏

**是什么**：大项目不是一次长会话，是几十次中断的接续。三类长跑问题各有对策：

1. **跨 task 上下文衰减**：长任务序列执行到中段，AI 对 spec/plan 的记忆会淡化。对策：定期让 AI **重读 spec.md + plan.md + 最近代码**再继续——回到规格，不凭记忆。
2. **中断再入场**（隔天/隔周回来）：固定入口动作 = 当次特性文档 + plan 进度标记 + 最近一份验收报告/变更总结（§3.7），三样读完再动手。H0 开工三读管第一次开工，这套管**每一次**再入。
3. **过程留痕**：每轮工作结束把关键提示词与决策追加进项目日志（示范工程的 prompt.md 即 241 条留痕的实物）——过程可回溯，也是再入场的上下文来源。

**成本与节奏**：把大项目切成"节"推进（示范工程即逐节开发，每节一个完整的 specify → implement → 验收闭环）。节奏本身就是成本控制：每节有独立验收，token 花费以节为预算单位可核算；节与节之间的停点，是评估"这节值不值、下节还这么干吗"的机会。

**怎么迁移**：再入口径写进项目 AI 指南；"每节一停"与 §3.3 停点原则同源；日志从第一天记（它同时喂 §3.12 的陷阱表）。

## 5. 使用边界

这套方法论（尤其 Spec-Kit 完整流程）的适用条件，原项目评估过，值得照抄这个诚实：

**适合**：

- medium-large 规模的 greenfield（从零开发、工程量跨多个模块）
- 需求清晰（上游有需求文档或明确产品决策）
- AI agent 做主体开发
- 团队需要沉淀工程方法论

**不适合**：

- 小 feature、快速原型、单文件改动——流程开销大于收益，切手动提示词模式（§3.10）
- 大型 brownfield 改造——legacy 上下文超出 LLM context limit
- 探索性研究项目——需求未定就跑 spec 会反复返工；同一条也适用于立项文档链：探索期应故意保持轻量、先跑通再冻结（§2 纪律 3）

**显式不管的**（按"一个人驱动 AI"校准的边界，声明在此以免误以为这些问题不存在）：

- **安全加固深度**：覆盖到依赖 CVE 扫描与凭证纪律（全局不变量层）；威胁建模、渗透测试、提示注入防护不在范围——企业部署时另行引入专项
- **多人/社区协作**：全文按单人驱动者校准。开源社区 PR 到来时，宪法的 PR 修订治理（§3.1）已预留接口，但 PR 评审与合并流程本身不在范围
- **多 agent 编排**：前提假设是单 agent + 人判软门禁；agent 之间的分工与互查不在范围
- **产品发布管理**：semver / changelog / release 流程留给项目自定，本文档只管宪法自身的版本治理

**工具层面的注意**：spec 工具链迭代快，实施前锁定一个具体版本，整个开发期间不升级；只用官方核心命令，不引入社区扩展。
